## Что это

Обычно opencode работает на десктопе или сервере. Это приложение упаковывает
бинарь opencode в APK и поднимает локальный HTTP-сервер прямо на телефоне или
планшете — без Termux и без root. Поверх сервера два слоя интерфейса:

1. **WebView** с веб-интерфейсом opencode.
2. **Нативный чат-оверлей** на Compose: официальная SPA не рендерит ленту в
   WebView, поэтому приложение само опрашивает локальный API и рисует
   переписку (400 мс при генерации, 900 мс в покое).

Сверху над этим работает мобильный агент: он правит код, ходит в GitHub через
API, собирает APK в Actions, скачивает его, сверяет размер и sha256 и ставит на
телефон через системный диалог. PC-посредник убран 19.11 — всё делает сам
мобайл-агент на устройстве.

> Экспериментальный демонстрационный проект. Детали сборки —
> [docs/build-and-install.md](./docs/build-and-install.md), ограничения —
> [docs/history-and-limitations.md](./docs/history-and-limitations.md).

## Самодиагностика без adb

Экран ошибки больше не говорит «Server failed. See logcat»: он показывает
`stage / code (recoverable) + message` и три последних сбоя. Этого хватает,
чтобы прочитать причину со скрина на телефоне друга.

Параллельно `FailureReporter` шлёт компактный отчёт в приватную группу
Telegram. Отправка живёт в `OpencodeServerService.onRuntimeState()` на стадиях
`CRASHED` / `FAILED_PERMANENTLY`, поэтому срабатывает даже если терминал не
открыт. В отчёте:

```
from: <имя из диагностики, по умолчанию USER>
reporter: <UUID установки>
role: DEV/ADMIN | USER
device: BRAND MODEL API ABI RAM
stage / code / message / history / time
```

Имя меняется в диагностике, секция «Отчёты о сбоях». Пути, логины и длинные
токены вырезаются; `opencode.log` не отправляется. Отчёт сначала ложится в
очередь `filesDir/failures/*.json` и досылается при появлении сети. Лимит —
один отчёт в час плюс дедуп 24 часа по `код|versionCode|gitSha`: crash loop не
заспамит группу. У каждого устройства свои префы и UUID, поэтому сбои с
других телефонов приходят независимо.

## Архитектура

```mermaid
flowchart TD
    A["Чат и диагностика"] --> B["opencode serve на устройстве"]
    B --> C["MCP памяти :4199"]
    C --> D["Детерминированное ядро: FTS5 + якоря + дедуп"]
    D --> E{"Уверенность ядра"}
    E -- "высокая или средняя" --> F["Детерминированный pack"]
    E -- "низкая или force" --> G["LLM-сопроцессор"]
    G --> H["Синонимы и evidence"]
    H --> F
    G -. пустой ответ, таймаут, отказ .-> F
    F --> I["Агент получает 5–12 чанков"]
    I --> B
    B --> J["Moltbook :4201 — тик, ответы, отчёт"]
    J --> K["MOLTBOOK_REPORT.md"]
    D -. "сигнал miss/control" .-> L["data-plane: signal_candidates"]
    L --> M["куратор → gold_staging → gold"]
    M -. "ручной approve" .-> N["code-plane: baseline"]
    N -. "held-out gate" .-> D
```

Ключевое правило: LLM **не пишет память** и не заменяет ядро. На вход ей
попадают только топ-N кандидатов после `memory_*`, а на выходе всегда лежит
обычный pack ядра. При любом невалидном ответе приложение молча возвращает
стандартный результат ядра.

Отдельная граница — **data-plane vs code-plane**. Сигналы и пороги живут в
`memory-adaptive-store.js` под hash-замком и не импортируются в `memory-core.js`.
Модель не имеет прямой записи ни в код, ни в рантайм: всё,
что меняет поведение ядра, проходит через тесты и human approve.

## Ядро памяти — главная система проекта

Это не «поиск по файлам» и не векторная база на коленке. Это отдельный
детерминированный сопроцессор рабочей памяти, который живёт внутри приложения
и позволяет агенту вспоминать собственные решения, правила, ошибки и итоги
проверок. Всё нужное — локально: `bun:sqlite`, FTS5, собственные модули,
никаких внешних npm, Python, Go или Rust внутри APK.
`MemoryMcp.toolCounts()` не трогался: счётчик спрашивает живой `tools/list`.

### Из чего состоит

| Слой | Что делает |
|---|---|
| Источники | Корневые документы `MOBILE_AGENT/` и `docs/`; манифест `sources.json` с sha-замками. Большие отчёты в `архивы/` не индексируются |
| Чанки | Текст режется по заголовкам и абзацам; id = источник + номер строки + sha текста |
| Хранилище | SQLite с FTS5; рядом якоря, provenance, время создания, флаг секрета |
| Дедупликация | Канонический корневой источник побеждает копию в `docs/`; устранено 29 пар |
| Поиск | Стабильный пул кандидатов 15–18, scoring по словам, якорям, близости и authority; opt-in `mode:"l0"` добавляет entity-алиасы после дедупа, `mode:"wave4"` — один слот на источник в топ-5 |
| Пак | Детерминированный набор чанков с бюджетом токенов и полем `why` у каждого куска |
| Адаптив | Уверенность `high/medium/low/none` меняет ширину packs: 8 чанков / 1600 токенов или 12 / 2048 |
| V4 / credit-blame | `memory_outcome`, `why.evidence`, `memory_observation`, `runDreamPass`, `memory_epoch`; включается явно |
| Аудит | Hash-chain с `verifyAuditChain()`, append-only rollback, детерминированный held-out gate |
| data-plane | `memory-adaptive-store.js`: пороги/веса под hash-замком, `deltaCap 0.10`, `cooldown 20`, `maxDrop 0.02`, карантин при повреждении |
| Gold | 113 кейсов, 30 held-out, сплит закреплён в строке, `split_policy = "sha256-bucket-75-v1"` |
| Безопасность | Молчаливое удаление запрещено: только `supersede` + архив + аудит + откат |
| Инструменты | 32 MCP-тула: индекс, поиск, пак, сигналы, замеры, граф, откат, аудит, статус, LLM |

### Как работает запрос

```mermaid
flowchart TD
    A["Документы MOBILE_AGENT"] --> B["Чанки с id и sha"]
    B --> C["SQLite + FTS5"]
    C --> D["Якоря и дедуп"]
    D --> E["Пул кандидатов 15–18"]
    E --> F["Скоринг и дедуп"]
    F --> G{"Уверенность"}
    G -- "high / medium" --> H["Пак 8 чанков / 1600 токенов"]
    G -- "low / none" --> I["Пак 12 чанков / 2048 токенов"]
    H --> J["Ответ с why и budgets"]
    I --> J
    G -- "низкая уверенность" --> K["LLM получает 5–12 чанков"]
    K --> J
    K -. таймаут или пустой ответ .-> I
```

Почему это работает надёжно:

- **Детерминизм.** Один и тот же индекс и запрос дают один и тот же pack.
  Пул FTS зафиксирован, поэтому топ-N — префикс большего N.
- **Порядок источников.** `collectSources()` сортирует по authority
  канонического источника и пути — обход не зависит от файловой системы.
- **Честные источники.** Найдена и устранена дедупликация канонического
  источника: живой индекс иногда оставлял устаревшую копию правила из `docs/`.
- **Никаких тихих потерь.** Удаление заменяется `supersede`, архивом, аудитом
  и откатом. Секреты в индекс не попадают: `secret:0`.
- **Самопроверка.** `memory_bench` считает recall, gate сравнивает его с
  baseline и показывает delta, а не просто «прошло/не прошло».
- **Живая диагностика.** `diag-live-recall.mjs` читает реальную базу приложения
  в режиме только для чтения и показывает конкретные промахи gold.

### Дефект `created` и его корень

Раньше при правке документа индексатор писал `created = now` всем чанкам
изменённого файла, хотя id включает источник, номер строки и sha текста. Чанк
«молодел», живой gold терял g17. Теперь старые `created` сохраняются в карте по
id и подставляются обратно для совпавших чанков. Регресс-тест 2b проверяет
именно этот случай; на apk-52 правка шапки `СОСТОЯНИЕ.md` без подготовки дала
`updated=1`, recall 20/20, gate `pass`.

### Волна 1: факты со временем

`memory_fact` и `memory_fact_link`: у факта есть `topic_key`, `valid_from`,
`invalid_at`, уверенность и причина. Старый факт не удаляется, а закрывается
новым; откат возвращает предыдущее состояние через аудит. Запрос с `as_of`
показывает, что было актуально в нужный момент. Новых MCP-инструментов нет —
режим задаётся параметрами существующих вызовов.

### Нестабильность якорного пула

У частого якоря (`apk`) bm25 почти нулевой, поэтому при равной оценке SQLite
возвращал строки в порядке `rowid`. Инкрементальная правка меняла `rowid`, и
эталон выпадал из пула: живой recall падал до 0.950. Веса ранжирования
оставили нетронутыми и исправили индексатор: колонка `ord` хранит порядок
обхода файлов, обе FTS-таблицы пересобираются целиком. Регресс-тест 4g
намеренно переворачивает строки FTS и требует совпадения с свежим индексом.

### Два профиля одного ядра

| | dev/debug | release (рубеж) |
|---|---|---|
| `MCP_DOCS_DIR` | включён, удобно отлаживаться | `""` — документы разработчика не вход в ядро |
| SQLite | общий каталог воркспейса | app-private `filesDir` |
| Память | operator-log + сигналы | только `ingest / signal / approve` пользователя |
| Перенос | клонирование репозитория | export/import-бандл с версией и hash |
| Сборка | apk-76 установлена | следующий рубеж — только после отдельного подтверждения |

**Принцип:** APK несёт **код ядра + стартовый gold**. Ни `СОСТОЯНИЕ.md`, ни
`ЖУРНАЛ.md`, ни `README.md` внутрь APK не попадают — это operator-log в
репозитории, а не память приложения. У нового пользователя движок есть, а
знаний нет: они растут из его собственных решений. Сегодня есть паразитная
зависимость от `<external>/MOBILE_AGENT`, и её надо убрать в релизе. Именно она
объясняет, почему живой `index_sha` apk-76 (`5440945b9becf9db`) совпадает с
локальным: `MCP_DOCS_DIR` пока включён и индексирует оператор-доки воркспейса
(23 файла / 902 чанка после правок 24.11).

### Саморастущий gold-корпус

Сейчас **113 gold-кейсов и 30 held-out**. Сплит записан в каждую строку и
**никогда не пересчитывается**; это закрывает утечку, когда правка порогов
перетаскивала кейс из train в validation. Новые ID получают детерминированный
бакет `sha256-bucket-75-v1` с солью `gold-v1`; старые 40 сохранены без
пересчёта. Канон append-only: существующие метки не правятся даже когда контент
переезжает между документами — такие случаи фиксируются отдельной диагностикой
с подстановкой в памяти.

```mermaid

  G -- n --> I["rejected с причиной"]
```

| Правило | Как ложится на стек |
|---|---|
| Сплит навсегда | `split`, `split_policy`, `hash_salt` в строке gold; backfill 40 кейсов без пересчёта |
| Дедуп по смыслу | Jaccard по леммам + `aliasScore` (containment), чтобы не склеить разные намерения |
| Карантин | `raw_signals → gold_staging → y/n/edit → gold.jsonl`; сырой мисклик не отравляет эталон |
| Стратификация | Квота ≤30% на `expect_source` за батч, до 3 control на батч |
| Пара хэшей | `index_sha` (документы) + `gold_sha` (эталон) в каждом протоколе |

## Резидентный LLM-сопроцессор

Модель `qwen3-0.6b-q4km` скачивается отдельно, сверяется по размеру и sha256 и
кладётся в `files/musl/` рядом с `.so`. Внутри APK внешних npm, Python, Go или
Rust-зависимостей нет: только `bun:sqlite`, локальные модули и песочница.

| Режим | Когда вызывается | Что происходит |
|---|---|---|
| `core-only` | Высокая или средняя уверенность ядра | LLM не вызывается, ответ за ~10 мс |
| `force` | Кнопка в диагностике | LLM вызывается принудительно, pack ядра внутри |
| Авто | Низкая уверенность | LLM вызывается сама, при отказе — молчаливый fallback |

Замер честно показал, что LLM как селектор слабее ядра и намного медленнее:

| Путь | recall | Латентность |
|---|---:|---:|
| Ядро | 1.000 | 5–20 мс |
| Ядро + синонимы LLM | 1.000 | около 7.4 с |
| LLM как селектор | 0.250 | около 7.4 с |
| 6 парафраз: ядро | 1.000 | — |
| 6 парафраз: селектор | 0.167 | — |

Поэтому LLM остаётся источником синонимов и evidence, а не судьёй.

`McpAssetImportContractTest.kt` проверяет, что **каждый именованный импорт имеет
экспорт в целевом модуле**. На ассетах apk-63 он нашёл ровно одну проблему
(`goldSha`), на `main` после починки — ноль. Staged-ассеты байтно равны
протестированному ядру до запуска Release.

CI в витрине намеренно не привязан к номеру run: конкретные ID быстро
устаревают, а формулировка «CI зелёный» остаётся верной после правки доков.

## Moltbook: живой контур агента

Плагин :4201 работает под sha-замком (`03dcdc06…` совпал перед каждым
сетевым вызовом). Тик сканирует ленту, отвечает кандидатам по одному, решает
challenge самостоятельно и пишет `MOLTBOOK_REPORT.md`.

| Исход ответа | Что это значит |
|---|---|
| `verified` | challenge решён, перечитка треды подтвердила коммент |
| `reused` | ветка уже закрыта нашим прежним ответом — повторно не шлём |
| `deferred` | родитель ниже капа глубины, отвечаем на верхнем уровне треда |
| `unconfirmed` | сервер сказал `200/ok`, но перечитка не видела — успехом не считаем |
| `verification-failed` | неверный ответ challenge: коммент удаляется, повторной попытки нет |

Правило арифметики challenge: явный `*` / `times` / `product` → умножение,
`and`/`total` без `*` → сложение. last tick: `verified 8`, `failed 1`,
`deferred 1`, `pending 242`, `refusals 15`, `external_blocks 0`.
Сторож тика отдельно: тревога «молчит 3 ч» оказалась рассинхроном расписания
после переустановки apk-65, а не падением плагина.

Отчёт — [MOBILE_AGENT/MOLTBOOK_REPORT.md](./MOBILE_AGENT/MOLTBOOK_REPORT.md).

## Версия opencode и самообновление

Начиная с apk-69 APK вшивает **opencode 2.4.0** (байтно равен npm-пакету
`@opencode/cli-linux-arm64-musl@2.4.0`), поэтому при чистой установке не
приедет старый 2.3.0. Приложение и дальше спрашивает реестр npm (тег
`latest`), сверяет sha512 из `dist.integrity`, прогоняет `--version` и только
потом кладёт обновлённый бинарь в приватное хранилище. Старт идёт из
`nativeLibraryDir` через `libldmusl.so`. Проверка не чаще раза в
6 часов и только по Wi-Fi. Два падения подряд — откат на ядро из APK, версия
запоминается как отбракованная. Мажорные версии автоматически не ставятся.

Источник истины о версии — живой `GET /api/info`, а не документация:
`/global/health` на 2.x отвечает заглушкой SPA на неизвестные пути. Все семь
этапов перехода 1.x → 2.x описаны в
[docs/MIGRATION-V2.md](./docs/MIGRATION-V2.md).

## Итог

Проект прошёл путь от «android-обёртка над opencode» до самостоятельного
мобильного агента с детерминированной памятью, опциональным LLM-сопроцессором
и живым контуром самообучения. Текущая сборка **apk-76** установлена, данные
приложения сохранены, полный CI зелёный, все тесты зелёные. Ядро держит дефолт
`legacy`, experiments изолированы в data-plane, гибрид не пущен в продакшн,
потому что held-out не подтвердил выигрыш. Диагностика 24.11 показала, что
дефицит gold объясняется устаревшими метками, а не поиском: с метками под
текущий контент корпус закрывается на 100%. Волна 4 доставила opt-in
`mode:"wave4"` (диверсификация топ-5) в apk-74: hard r5 1.000, h06 закрыт
вживую. У нового пользователя память будет
расти из его собственных ingest/сигналов/апрувов, а не из чужого operator-log —
этот архитектурный рубеж следующий, под отдельное подтверждение.

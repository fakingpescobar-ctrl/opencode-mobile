сортируются детерминированно: `collectSources()` кладёт канонические документы

помощники работают в фоне, а под «Модель думает…» появляется строка

код, ссылки, цитаты, списки), а сами ссылки — и `[подпись](url)`, и голые
`https://...` — открываются по тапу в системном браузере.

**В работе после apk-61 (локально, ещё не в APK):** ядро памяти стало
автономным и самообучаемым. Закрытый контейнер источников с sha-замками
(`memory/sources.json`) и точка старта `bootContainer()` — правка доков больше не
меняет память молча. Движок v2 поверх детерминированного FTS5: компактная карта
памяти (агент знает, о чём речь, без полного обхода), self-supervised mining
закономерностей «термин → источник» и meta-learning поощрений/штрафов сигналов.
`approve` гоняет held-out gate с авто-откатом по `audit_id`, kind-якорь и обход
по графу работают как раньше. Стабильный замер: холодный 0.850 / **0.503**,
после credit/blame 0.950 / **0.647**. Тесты **291/0 + 123/0 + 109/0**.

## Что это

Обычно opencode работает на десктопе или сервере. Это приложение упаковывает
бинарь opencode в APK и поднимает локальный HTTP-сервер прямо на телефоне или
планшете — без Termux и без root. Поверх сервера два слоя интерфейса:

1. **WebView** с веб-интерфейсом opencode.
2. **Нативный чат-оверлей** на Compose: официальная SPA не рендерит ленту в
   WebView, поэтому приложение само опрашивает локальный API и рисует
   переписку (400 мс при генерации, 900 мс в покое).

Сверху над этим работает мобильный агент: он правит код, ходит в GitHub через
API, собирает APK в Actions, скачивает его, сверяет размер и sha256 и ставит на
телефон через системный диалог. PC-посредник убран 19.11 — всё делает сам
мобайл-агент на устройстве.

> Экспериментальный демонстрационный проект. Детали сборки —
> [docs/build-and-install.md](./docs/build-and-install.md), ограничения —
> [docs/history-and-limitations.md](./docs/history-and-limitations.md).

## Самодиагностика без adb

Экран ошибки больше не говорит «Server failed. See logcat»: он показывает
`stage / code (recoverable) + message` и три последних сбоя. Этого хватает,
чтобы прочитать причину со скрина на телефоне друга.

Параллельно `FailureReporter` шлёт компактный отчёт в приватную группу
Telegram. Отправка живёт в `OpencodeServerService.onRuntimeState()` на стадиях
`CRASHED` / `FAILED_PERMANENTLY`, поэтому срабатывает даже если терминал не
открыт (белый экран — как раз такой случай). В отчёте:

```
from: <имя из диагностики, по умолчанию USER>
reporter: <UUID установки>
role: DEV/ADMIN | USER
device: BRAND MODEL API ABI RAM
stage / code / message / history / time
```

Имя меняется в диагностике, секция «Отчёты о сбоях». Пути, логины и длинные
токены вырезаются; `opencode.log` не отправляется. Отчёт сначала ложится в
очередь `filesDir/failures/*.json` и досылается при появлении сети. Лимит —
один отчёт в час плюс дедуп 24 часа по `код|versionCode|gitSha`: crash loop не
заспамит группу. У каждого устройства свои префы и UUID, поэтому сбои с
других телефонов приходят независимо. Токен бота считается публичным: у него
нет прав вне группы, при спаме он просто ротируется.

```mermaid
flowchart TD

    B --> C["MCP памяти :4199"]
    C --> D["Ядро: FTS5 + якоря + дедуп"]
    D --> E{"Уверенность ядра"}
    E -- "высокая или средняя" --> F["Детерминированный pack"]
    E -- "низкая или force" --> G["LLM-сопроцессор"]

    F --> I["Агент получает 5–12 чанков"]
```

Ключевое правило: LLM **не пишет память** и не заменяет ядро. На вход ей
попадают только топ-N кандидатов после `memory_*`, а на выходе всегда лежит
обычный pack ядра. При любом невалидном ответе приложение молча возвращает
стандартный результат ядра.

## Ядро памяти — главная система проекта

Это не «поиск по файлам» и не векторная база на коленке. Это отдельный
детерминированный сопроцессор рабочей памяти, который живёт внутри приложения
и позволяет агенту вспоминать собственные решения, правила, ошибки и итоги
проверок. Всё нужное — локально: `bun:sqlite`, FTS5, собственные модули,
никаких внешних npm, Python, Go или Rust внутри APK. `MemoryMcp.toolCounts()`
не трогался: счётчик спрашивает живой `tools/list` у сервера.

### Из чего состоит

| Слой | Что делает |
|---|---|
| Источники | Корневые документы `MOBILE_AGENT/` и `docs/`. Большие отчёты лежат в `архивы/` и сознательно не индексируются |
| Чанки | Текст режется по заголовкам и абзацам; id = источник + номер строки + sha текста |
| Хранилище | SQLite с FTS5; рядом лежат якоря, provenance, время создания и флаг секрета |
| Дедупликация | Канонический корневой источник побеждает копию в `docs/`; устранено 29 пар |
| Поиск | Стабильный пул кандидатов 15–18, scoring по словам, якорям, близости и authority |
| Пак | Детерминированный набор чанков с бюджетом токенов и полем `why` у каждого куска |
| Адаптив | Уверенность `high/medium/low/none` меняет ширину packs: 8 чанков / 1600 токенов или 12 / 2048 |
| Безопасность | Молчаливое удаление запрещено: только `supersede` + архив + аудит + откат |
| Инструменты | Индекс, переиндексация, поиск, пак, замеры, граф, откат, аудит, статус и поиск LLM |

### Как работает запрос

```mermaid
flowchart TD
    A["Документы MOBILE_AGENT"] --> B["Чанки с id и sha"]
    B --> C["SQLite + FTS5"]
    C --> D["Якоря и дедуп"]
    D --> E["Пул кандидатов 15–18"]
    E --> F["Скоринг и дедуп"]
    F --> G{"Уверенность"}
    G -- "high / medium" --> H["Пак 8 чанков / 1600 токенов"]
    G -- "low / none" --> I["Пак 12 чанков / 2048 токенов"]
    H --> J["Ответ с why и budgets"]
    I --> J
    G -- "низкая уверенность" --> K["LLM получает 5–12 чанков"]
    K --> J
    K -. таймаут или пустой ответ .-> I
```

Почему это работает надёжно:

- **Детерминизм.** Один и тот же индекс и запрос дают один и тот же pack.
  Раньше `recallDocs` был немонотонным по `limit`: пул FTS равнялся
  `limit*3`, поэтому топ-5 и топ-12 ранжировали разные наборы. Пул зафиксирован,
  теперь топ-N — префикс большего N.
- **Порядок источников.** `collectSources()` сортирует файлы по убыванию
  `AUTHORITY[kindOf(rel)]`, затем по `rel`. Простая сортировка по пути роняла
  эталон `АРХИТЕКТУРА_ПАМЯТИ.md` из топ-5, поэтому канонические документы
  идут первыми независимо от порядка в файловой системе.
- **Честные источники.** Найдена и устранена дедупликация канонического
  источника: живой индекс иногда оставлял устаревшую копию правила из `docs/`.
- **Никаких тихих потерь.** Удаление заменяется `supersede`, архивом, аудитом
  и откатом. Секреты в индекс не попадают: `secret:0`.
- **Самопроверка.** Встроенный `memory_bench` считает recall, gate сравнивает
  его с baseline и показывает delta, а не просто «прошло/не прошло».
- **Живая диагностика.** `diag-live-recall.mjs` читает реальную базу приложения
  в режиме только для чтения и показывает конкретные промахи gold.

**Итог по ядру.** Мы прошли путь от расхождения живого и свежего индекса
(`g02`, `g06`, `g11`, `g17`, `g20`) до полного совпадения: живой recall 1.000,
жёсткий gold 20/20, 198/100/109 тестов, gate `pass` и ни одной внешней
зависимости. Это та часть проекта, которую можно показать как отдельную
систему: она воспроизводима, проверяема и восстанавливаема.

### Дефект `created` и его корень

Раньше при правке документа индексатор писал `created = now` всем чанкам
изменённого файла, хотя id чанка включает источник, номер строки и sha текста.
Из-за этого один и тот же чанк «молодел», и живой gold терял g17. Обход с
выравниванием mtime работал, но требовал ручного ритуала.

Теперь старые `created` сохраняются в карту по id и подставляются обратно для
совпавших чанков. Регресс-тест 2b в `memory-core.test.mjs` проверяет именно
этот случай. Проверка вживую на apk-52: правим шапку `СОСТОЯНИЕ.md`,
переиндексируем без подготовки — `updated=1`, recall 20/20, gate `pass`.

### Волна 1: факты со временем

Появились `memory_fact` и `memory_fact_link`: у факта есть `topic_key`,
`valid_from`, `invalid_at`, уверенность и причина. Старый факт не удаляется, а
закрывается новым; откат возвращает предыдущее состояние через аудит. Запрос с
`as_of` показывает, что было актуально в нужный момент, а не только последнюю
запись. `memory_pack` подмешивает активные факты. Новых MCP-инструментов нет —
режим задаётся параметрами существующих вызовов, `MemoryMcp.toolCounts()` не
тронутся. Временно́й gold: 16/16.

### Нестабильность якорного пула

У частого якоря (`apk`) bm25 почти нулевой во всех чанках, поэтому при равной
оценке SQLite возвращал строки в порядке `rowid`. Инкрементальная правка меняла
`rowid`, и эталон выпадал из пула: живой recall падал до 0.950 при том же коде
и тех же текстах. Пять вариантов правки ранжирования не прошли тесты, поэтому
веса оставили нетронутыми и исправили индексатор: колонка `ord` хранит порядок
обхода файлов, а обе FTS-таблицы пересобираются целиком в этом порядке.
Регресс-тест 4g намеренно переворачивает строки FTS и требует, чтобы после
индексации выдача совпала со свежим индексом. Живой core 1.000 / gate `pass`,
hard gold 1.000 по всем четырём метрикам.

## Резидентный LLM-сопроцессор

Модель `qwen3-0.6b-q4km` скачивается отдельно, сверяется по размеру и sha256 и
кладётся в `files/musl/` рядом с `.so`. Внутри APK внешних npm, Python, Go или
Rust-зависимостей нет: только `bun:sqlite`, локальные модули и песочница.

| Режим | Когда вызывается | Что происходит |
|---|---|---|
| `core-only` | Высокая или средняя уверенность ядра | LLM не вызывается, ответ за ~10 мс |
| `force` | Кнопка в диагностике | LLM вызывается принудительно, pack ядра внутри |
| Авто | Низкая уверенность | LLM вызывается сама, при отказе — молчаливый fallback |

Замер честно показал, что LLM как селектор слабее ядра и намного медленнее:

| Путь | recall | Латентность |
|---|---:|---:|
| Ядро | 1.000 | 5–20 мс |
| Ядро + синонимы LLM | 1.000 | около 7.4 с |
| LLM как селектор | 0.250 | около 7.4 с |
| 6 парафраз: ядро | 1.000 | — |
| 6 парафраз: селектор | 0.167 | — |

Поэтому LLM остаётся источником синонимов и evidence, а не судьёй. Плотные
эмбеддинги не подключались: на 20 жёстких и 20 обычных gold конкретных
семантических провалов не найдено. Точка с эмбеддингами закрыта до появления
реальных провалов из практики.

## Версия opencode и самообновление

APK вшивает ядро 2.3.0, но приложение само спрашивает реестр npm
(`@opencode/cli-linux-arm64-musl`, тег `latest`), сверяет sha512 из
`dist.integrity`, прогоняет `--version` и только потом кладёт бинарь в
`filesDir/core/libopencode.so`. Проверка не чаще раза в 6 часов и только по
Wi-Fi. Два падения подряд — откат на ядро из APK, версия запоминается как
отбракованная. Мажорные версии автоматически не ставится.

Источник истины о версии — живой `GET /api/info`, а не документация:
`/global/health` на 2.x отвечает заглушкой SPA на неизвестные пути. Все семь
этапов перехода 1.x → 2.x описаны в
[docs/MIGRATION-V2.md](./docs/MIGRATION-V2.md).

## Итог

Проект прошёл путь от «/android-обёртка над opencode» до самостоятельного
мобильного агента с детерминированной памятью и опциональным LLM-сопроцессором.
Текущая сборка apk-61 установлена, данные приложения сохранены, полный CI
зелёный, метрики на потолке. В чате Answer-реплики красятся по markdown, а
ссылки открываются в браузере по тапу; ядро индексирует источники в
детерминированном порядке. Сбои сами приходят в приватную группу Telegram с
ролью, UUID установки и подписью отправителя — диагностика друга больше не
требует ни adb, ни компьютера. Следующий шаг по эмбеддингам осознанно отложен
до реальных провалов в практике.

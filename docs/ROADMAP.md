# Дорожная карта: opencode-mobile → продукт для чужих телефонов

Три трека по честным хвостам. Каждый — шаги, файлы, критерий готовности.

Порядок внедрения: **Трек 1 (release) → Трек 2 (сеть) → Трек 3 (turbo)**.
Release-контур блокирует «дать человеку», сеть блокирует «мобильный opencode»,
турбо — перф.

---

## Трек 1 — Release-контур (самый важный, делаем первым)

**Боль:** debug-APK 392MB, пакет `.debug`, `isMinifyEnabled=false`.

### 1. Release-минифицирование с `.so` без поломки
- Включить `isMinifyEnabled=true` + `shrinkResources=true` в `release` блоке
  (`app/build.gradle.kts`, строчки ~20-26).
- **Критично:** `libopencode.so` и whisper `.so` лежат в `jniLibs` — R8 их не
  трогает (только dex), но проверить, что `packaging { jniLibs.useLegacyPackaging }`
  не слетел (execve из `nativeLibraryDir`).
- Добавить `keep`-правила для рефлексии (opencode serve пути) в
  `proguard-rules.pro`.
- Ожидание: `material-icons-extended` (2000+ иконок) R8 выкинет неиспользуемые
  → экономия ~20-30MB dex.

### 2. Честный размер модели
- ✅ **base вынесена из APK** в lazy-скачивание (как turbo). APK: 374 → 274 (R8) → **147 MB**.
- Реальный предел — ~147MB, т.к. `libopencode.so` (184 MB) — это сам opencode,
  вынести нельзя. Дальнейшие варианты:
  - **App Bundle / on-demand** (Play требует AAB) — ещё ужимает загрузку.
  - Опционально: **убрать `libbun-musl.so` (70MB)** если opencode может работать
    без bun-браузинга (рискованно, требует проверки запуска serve без bun).

### 3. Release-сборка и подпись
- `applicationIdSuffix` убрать из release (сейчас только debug имеет `.debug` —
  ок, release будет чистый `org.opencode.mobile`).
- Создать signing config (upload key), беймпинг `versionCode`/`versionName` (0.1.x).
- Собрать `assembleRelease`, прогнать smoke-тест на устройстве: запуск, чат, STT.

**Готово когда:** `assembleRelease` даёт APK/AAB ~100MB (или lazy ~70MB),
пакет чистый, всё работает под smoke-тестами на телефоне.

## Трек 2 — Сеть без ручного прокси

**Боль:** на Android нет `/etc/resolv.conf`, musl шлёт на `127.0.0.1:53`,
внешние сервисы не ходят без прокси.

**✅ Реализовано.** Встроенный `Ipv4Proxy` (CONNECT-туннель на `127.0.0.1:3128`,
IPv4-first через `InetAddress`/Netd) + `HTTPS_PROXY`/`HTTP_PROXY`/`NO_PROXY` в
`OpencodeRuntime.startServe`. Подтверждено на устройстве: туннели к
`mcp.context7.com`, `mcp.grep.app`, `registry.npmjs.org` открываются автоматически.

Остатки (опционально):
- Прогнать явный `webfetch`/`git` из чата на реальном телефоне как регресс-тест.

**Готово:** внешние вызовы opencode ходят в сеть без ручного прокси-конфига.

## Трек 3 — STT turbo на CPU

**Боль:** большие модели душатся до 1-5% (ColorOS/OPPO), turbo медленный.

### 6. ncnn-int8 для энкодера
- ✅ **Внедрено** (следовали `tools/ncnn-int8-plan.md`; KV-cache уже был). int8-encoder
  (block-quant) грузится сразу в сеть (при неудаче — откат fp32), замерено:
  **int8-CPU 8.82 s vs fp32-CPU 17.9 s (~2×)**, int8-Vulkan 6.45 s (эксперимент,
  в проде выключен — см. `docs/EXPERIMENTS-STT-LATENCY.md` §2).
- Исполнитель: `ModelDownloader` качает int8-варианты турбо; `ncnn_jni.cpp::load()`
  выбирает их автоматически.

### 7. Многопоточность / foreground / потоковый пайплайн
- `WhisperTranscribeService` уже держит приоритет (foreground).
- ✅ **Потоковый пайплайн/чанкинг внедрён (ЭКСП-5, сентябрь 2026)**:
  `SpeechSegmenter` (VAD по RMS) + `ChunkedTranscriber` — длинная речь режется
  на сегменты, каждый распознаётся отдельно: первые слова видны на 1–2 s,
  хвост >30 с не теряется, галлюцинаций на тишине меньше.
- ✅ **Бенч turbo int8 на реальном OPPO прогнан** (24.09.2026): int8 6.8–8.2 s
  vs fp32 14.5–15.2 s (~2.1×); CSV: `docs/stt-bench-2026-09-24.csv`.
- Осталось: WER-бенч (точность при чанкинге), тюнинг `setThreads` на других
  устройствах.
- ✅ **VAD-пороги измерены, а не угаданы** (26.09.2026): офлайн-свип
  `SpeechSegmenterBenchTest` на реальных bench-wav, 6 порогов × 5 SNR = 30 замеров.
  Recall речи 90.7% на всём диапазоне 0.010–0.030; 0.015 и 0.025 дают **идентичный**
  результат во всех 30 замерах, то есть предложенный сдвиг порога — no-op.
  `MIN_RMS` остаётся 0.015. Отчёт: `app/build/reports/vad-bench.txt`.
- ⛔ **WER-бенч по-прежнему невозможен**: нужны эталонные транскрипты, которых в репозитории
  нет, плюс устройство с моделями для ncnn-прохода. Считать WER по выводу модели нельзя —
  на `jfk.wav` int8 отдаёт текст, не являющийся цитатой.

**Готово когда:** потоковый пайплайн с первым результатом 1–2 s + WER-прогон —
✅ пайплайн внедрён (1–2 s первые слова); пороги VAD измерены; остаётся формальный
WER-бенч, заблокированный отсутствием эталона.

## Дополнительный трек — безопасность и память (сентябрь 2026)

- Единый клиент `LocalOpenCodeClient` (auth в одном месте).

  `RuntimeValidation` (`GET /mcp` → 2xx).

## День 2 — регресс-тесты и два расследования (01.10.2026)

Хвост после сессии «холодный запуск Яндекс.Музыки» (`69ae486`, `994053b`).
Проверено на устройстве: BAL обойдён через ручной `SYSTEM_ALERT_WINDOW` grant,
холодный старт при убитой ЯМ и фоне — 53 с и 81 с без `BAL_BLOCK`.

### Что выяснено при инвентаризации тестов

- ⛔ **`AppInstallBridgeTest.kt` не существует вообще.** На все роуты моста,
  разбор JSON и сериализацию тестов нет — то есть на весь код, который эта сессия
  добавила и который ломался дважды.
- ⛔ **В `ynison.js` нет ни одного экспорта.** Все 48 существующих JS-кейсов
  (`announce` 22, `goaway` 7, `search` 15, `session` 4) работают приёмом
  «вырезать блок исходника по маркерам» (`loadBlock` + `BLOCK_START`/`BLOCK_END`).
  `bridge()`, `opSessionStatus`, `opSessionControl` покрыты **нулём**.
- ✅ `play_pause` уже покрыт: в `MediaControlContracts` `ALIASES` содержит и
  `play_pause`, и `play-pause`, и `toggle`, а `MediaControlRequestValidatorTest`
  сверяет список wire-имён. Пункт «добавить тест на play_pause» вычеркнут.
- ⛔ `McpMusicConfigTest` не содержит ни одного утверждения про `TIMEOUT`.

### P0 — закрыть регрессы тестами

Новый `app/src/test/java/.../installer/AppInstallBridgeTest.kt`:
1. `jsonObject()` на пустом теле → `{}` (был 500, GET без body падал)
2. `JSONException` → 400, не 500; порядок catch-блоков
   (`JSONException` **не** наследник `IllegalArgumentException`)
3. `ok` в `/v1/apps/launch` — литерал `true`, не зависит от признака жизни.
   Это CRITICAL-регресс: ложный сигнал попал в поле `ok`, а `memory.js` кидает
   на `!body.ok` — `mobile_launch_app` падал на каждом вызове, а объяснение
   про BAL до агента не доходило
4. `toJson` отдаёт `background_launch_allowed` и **не** отдаёт `running`
5. `media.verified` вложен в `media`, не в корень (читался `undefined` →
   ложный «NOT verified»)

JS (после решения по seam):
6. `bridge()` не шлёт body на GET/HEAD
7. `clearTimeout` на **всех** путях (успех/ошибка/парсинг) — иначе таймер течёт
8. компактный 3-строчный вывод `opSessionStatus` + фильтр по `controlable`
9. **Кросс-языковая сверка:** enum `session_control` в `ynison.js` ==
   `MediaCommand.values().map { it.wireName }`. Сейчас источника истины два,
   и проверяется только Kotlin-сторона — JS разъедется молча. Ровно тот класс
   расхождения, который стоил C2.

**Готово когда:** `build.ps1 -Task jstest` зелёный, новый тест в `./gradlew test`,
и каждый тест проверен на «ловит ли сломанный код» — откат фикса должен давать
красный тест. Иначе это декоративные тесты, которые зеленеют на любом коде.

### P1 — расследования, не правки

**Effective-конфиг MCP.** `/data/data/.../opencode.jsonc` на устройстве не
содержит `ynison`, хотя инструменты `music_*`/`session_*` работают. Источник
не найден → `YNISON_MCP_TIMEOUT_MS = 180000` не подтверждён как действующий.
Порядок: найти, кто собирает финальный конфиг (рантайм-генерация, приходит с
сервера, merge, кэш) → **отдельно** замерить, где рвётся таймаут (клиент,
MCP-прослойка или сервер). Таймаут не чинить, пока не найден источник конфига.

Зацепка из прошлых сессий: `RuntimeManager` уже умеет fail-closed на конфиге —
ответ может лежать там. И отдельно: в `mem:opencode-mobile-installer-final-20260925`
замечено, что 15-минутный опрос установщика может превысить таймаут MCP-клиента.
Два независимых наблюдения одного класса — возможно, проблема не в `ynison`.

**Seed/mirror-цикл `ensurePhone()`.** Ynison может ответить зеркалом собственных
announce-вызовов, и клиент примет это за live-state → риск потери состояния живой
сессии. Воспроизвести `tools/ym-exp.ps1 -Variant nowrite` / `-Variant nohandback`,
найти точку подмены, потом минимальный фикс. Правка без воспроизведения —
гадание, поэтому сначала эксперимент.

### P2 — если останется время

- ⛔ **Playback >100 с после холодного старта** не проверен: только короткие прогоны.
  Живой вопрос — деградация позиции, потеря сессии, обрыв MCP-вызова.
- Мёртвый код: `AppInstallBridge.mediaApps` игнорирует поле `limit` и всегда берёт
  `DEFAULT_LIST_LIMIT = 50` (поле вводит в заблуждение — убрать или читать честно);
  `MEDIA_ACTIONS` в `memory.js` не используется, `mobile_media_control` отозван.
- Гигиена памяти проекта: поправка к устаревшей записи заведена
  (`mem:media-bridge-cleanup-correction-2026-10-01`), но правила нет. Минимум —
  даты коммитов в самих записях.

**Нужно от пользователя перед стартом P1:** разблокированный телефон с выданным
SAW-грантом (после `adb install -r` accessibility на ColorOS сбрасывается —
переставлять secure-настройки), разрешение убивать Яндекс.Музыку в экспериментах.
Реалистично за день — P0 плюс один из P1: разбор effective-конфига может
оказаться задачей на неделю.

### ⛔ Чего делать нельзя

Не «переизобретать» определение живости процессов. `/proc` на устройстве смонтирован
с `hidepid=invisible`, поэтому файл **живого** чужого процесса не читается
(`Permission denied`), и `pidof` отдаёт PID не того процесса. Признак жизни берётся
у цели — её MediaSession. Обходных путей нет: `getRunningAppProcesses` с API 21
отдаёт только своё приложение, `UsageStatsManager` требует второго grant.
Предупреждение есть комментарием в `InstalledAppController.kt`.

# Дорожная карта: opencode-mobile → продукт для чужих телефонов

Три трека по честным хвостам. Каждый — шаги, файлы, критерий готовности.

Порядок внедрения: **Трек 1 (release) → Трек 2 (сеть) → Трек 3 (turbo)**.
Release-контур блокирует «дать человеку», сеть блокирует «мобильный opencode»,
турбо — перф.

Отдельно, вне этих трёх треков: **Трек 4 — миграция на OpenCode 2**,
план в `docs/MIGRATION-V2.md`. Приложение пакует бинарь `serve` внутрь APK.
**Этапы 0–4 закрыты: в APK уже opencode 2.0.27**, HTTP-слой перенесён на `/api/*`
(`/session/status` удалён — статус синтезируется из псевдо-сообщения `type:"idle"`),
вопросы и разрешения остались на v1-ветке через `ApiPaths.active.legacy`.
Открытые этапы — 5–7. Риск WebView **снят**: SPA v2 грузится и работает.

## Трек 1 — Release-контур (самый важный, делаем первым)

**Боль:** debug-APK 392MB, пакет `.debug`, `isMinifyEnabled=false`.

### 1. Release-минифицирование с `.so` без поломки
- Включить `isMinifyEnabled=true` + `shrinkResources=true` в `release` блоке
  (`app/build.gradle.kts`, строчки ~20-26).
- **Критично:** `libopencode.so` и whisper `.so` лежат в `jniLibs` — R8 их не
  трогает (только dex), но проверить, что `packaging { jniLibs.useLegacyPackaging }`
  не слетел (execve из `nativeLibraryDir`).
- Добавить `keep`-правила для рефлексии (opencode serve пути) в
  `proguard-rules.pro`.
- Ожидание: `material-icons-extended` (2000+ иконок) R8 выкинет неиспользуемые
  → экономия ~20-30MB dex.

### 2. Честный размер модели
- ✅ **base вынесена из APK** в lazy-скачивание (как turbo). APK: 374 → 274 (R8) → **147 MB**.
- Реальный предел — ~147MB, т.к. `libopencode.so` (184 MB) — это сам opencode,
  вынести нельзя. Дальнейшие варианты:
  - **App Bundle / on-demand** (Play требует AAB) — ещё ужимает загрузку.
  - Опционально: **убрать `libbun-musl.so` (70MB)** если opencode может работать
    без bun-браузинга (рискованно, требует проверки запуска serve без bun).

### 3. Release-сборка и подпись
- `applicationIdSuffix` убрать из release (сейчас только debug имеет `.debug` —
  ок, release будет чистый `org.opencode.mobile`).
- Создать signing config (upload key), беймпинг `versionCode`/`versionName` (0.1.x).
- Собрать `assembleRelease`, прогнать smoke-тест на устройстве: запуск, чат, STT.

**Готово когда:** `assembleRelease` даёт APK/AAB ~100MB (или lazy ~70MB),
пакет чистый, всё работает под smoke-тестами на телефоне.

## Трек 2 — Сеть без ручного прокси

**Боль:** на Android нет `/etc/resolv.conf`, musl шлёт на `127.0.0.1:53`,
внешние сервисы не ходят без прокси.

**✅ Реализовано.** Встроенный `Ipv4Proxy` (CONNECT-туннель на `127.0.0.1:3128`,
IPv4-first через `InetAddress`/Netd) + `HTTPS_PROXY`/`HTTP_PROXY`/`NO_PROXY` в
`OpencodeRuntime.startServe`. Подтверждено на устройстве: туннели к
`mcp.context7.com`, `mcp.grep.app`, `registry.npmjs.org` открываются автоматически.

Остатки (опционально):
- Прогнать явный `webfetch`/`git` из чата на реальном телефоне как регресс-тест.

**Готово:** внешние вызовы opencode ходят в сеть без ручного прокси-конфига.

## Трек 3 — STT turbo на CPU

**Боль:** большие модели душатся до 1-5% (ColorOS/OPPO), turbo медленный.

### 6. ncnn-int8 для энкодера
- ✅ **Внедрено** (следовали `tools/ncnn-int8-plan.md`; KV-cache уже был). int8-encoder
  (block-quant) грузится сразу в сеть (при неудаче — откат fp32), замерено:
  **int8-CPU 8.82 s vs fp32-CPU 17.9 s (~2×)**, int8-Vulkan 6.45 s (эксперимент,
  в проде выключен — см. `docs/EXPERIMENTS-STT-LATENCY.md` §2).
- Исполнитель: `ModelDownloader` качает int8-варианты турбо; `ncnn_jni.cpp::load()`
  выбирает их автоматически.

### 7. Многопоточность / foreground / потоковый пайплайн
- `WhisperTranscribeService` уже держит приоритет (foreground).
- ✅ **Потоковый пайплайн/чанкинг внедрён (ЭКСП-5, сентябрь 2026)**:
  `SpeechSegmenter` (VAD по RMS) + `ChunkedTranscriber` — длинная речь режется
  на сегменты, каждый распознаётся отдельно: первые слова видны на 1–2 s,
  хвост >30 с не теряется, галлюцинаций на тишине меньше.
- ✅ **Бенч turbo int8 на реальном OPPO прогнан** (24.09.2026): int8 6.8–8.2 s
  vs fp32 14.5–15.2 s (~2.1×); CSV: `docs/stt-bench-2026-09-24.csv`.
- Осталось: WER-бенч (точность при чанкинге), тюнинг `setThreads` на других
  устройствах.
- ✅ **VAD-пороги измерены, а не угаданы** (26.09.2026): офлайн-свип
  `SpeechSegmenterBenchTest` на реальных bench-wav, 6 порогов × 5 SNR = 30 замеров.
  Recall речи 90.7% на всём диапазоне 0.010–0.030; 0.015 и 0.025 дают **идентичный**
  результат во всех 30 замерах, то есть предложенный сдвиг порога — no-op.
  `MIN_RMS` остаётся 0.015. Отчёт: `app/build/reports/vad-bench.txt`.
- ⛔ **WER-бенч по-прежнему невозможен**: нужны эталонные транскрипты, которых в репозитории
  нет, плюс устройство с моделями для ncnn-прохода. Считать WER по выводу модели нельзя —
  на `jfk.wav` int8 отдаёт текст, не являющийся цитатой.

**Готово когда:** потоковый пайплайн с первым результатом 1–2 s + WER-прогон —
✅ пайплайн внедрён (1–2 s первые слова); пороги VAD измерены; остаётся формальный
WER-бенч, заблокированный отсутствием эталона.

**Effective-конфиг MCP — источник найден (25.10.2026), замеры ждут телефон.**

Прежняя формулировка («`/data/data/.../opencode.jsonc` не содержит `ynison`,
источник не найден») описывала не тот файл. Конфиг целиком пишет приложение:

| Путь | Кто пишет | Роль |
|---|---|---|
| `<filesDir>/opencode-config/opencode/opencode.jsonc` | `OpencodeRuntime.ensureMcpConfig` | **действующий**: serve стартует с `XDG_CONFIG_HOME=<filesDir>/opencode-config` (`startServe`) |

opencode 2.0.27 (бинарь `@opencode/cli-linux-arm64-musl@2.0.27`, объект

Defaults to 5000»; в документации opencode то же поле у remote-серверов. То есть
приложение пишет не мёртвый ключ. Имя и значение закреплены тестом

**26.10.2026 — найдена настоящая причина «state open timeout»: сокет состояния шёл не туда.**

Вызов музыки висел 97,7 с и падал `state open timeout, buffered 0B`. Диагностика (ярлык
`state`/`redirect` в каждой строке трассы, статусная строка ответа, отказ по закрытию
соединения вместо 10-секундного таймера) показала: редирект-сокет работает целиком — 101,
payload, тикет, закрытие; а state-сокет получает **0 байт за 10 с**.

Причина: state-сервис отвечает только на адресе шарда. Приложение резолвит
`ynison.music.yandex.ru` (фронтенд) и передаёт этот IP в `ynison.js` (`RESOLVED_YNISON_IP`),
а Host/SNI у state-сокета — шардовый `k3t3i6….ynison.music.yandex.ru`. Фронтенд принимает
TLS и запрос и **не отвечает вообще**. Замер с PC при одинаковых Host, пути и токене:
фронтенд `77.88.21.101` — 0 байт, таймаут 6 с; шард `77.88.48.156` — `101 Switching
Protocols` за 0,16 с. DNS: фронтенд → `77.88.21.101`, шард → `77.88.48.156`.

Заодно снят миф, на котором стоял `resolveIpv4` — «musl-Bun не умеет DNS на Android»: на
устройстве `dns.lookup("k3t3i6….ynison.music.yandex.ru")` → `77.88.48.156` (тот же bun
запущен под `run-as`). Поэтому резолв шарда делается в JS, а не приходит снаружи.

Исправлено: `resolveStateHost()` резолвит шард на месте и отдаёт его адрес в state-сокет;
при отказе резолва — именованная ошибка вместо тишины. `ws.onclose` до апгрейда теперь
отклоняет промис (`state socket closed before upgrade`): раньше любой ранний разрыв
выглядел как таймаут.

Проверено на устройстве 26.10.2026: `state host: … -> 77.88.48.156` → `state connect` →
`state head: HTTP/1.1 101 Switching Protocols`; вызов вернулся за **7,86 с** вместо 97,7 с.
Ответ сервера при этом `500140000` / «stay away 3600s» — Ynison сам просит подождать
(устройство насобирало сессий за отладку), второй вызов подряд отказывает за 0,07 с без
нового соединения. Сквозной прогон музыки — после интервала.

**Пробный вызов продлевает бан на новый час.** Через час после первого бана (дедлайн
02:56:58) один `music_play_query` вернулся за 7,2 с с текстом «token is valid — wait out the
interval» и перезапустил блокировку до 03:57:20. Значит «проверить, пустило ли» нельзя:

### ⛔ Чего делать нельзя

Не «переизобретать» определение живости процессов. `/proc` на устройстве смонтирован
с `hidepid=invisible`, поэтому файл **живого** чужого процесса не читается
(`Permission denied`), и `pidof` отдаёт PID не того процесса. Признак жизни берётся
у цели — её MediaSession. Обходных путей нет: `getRunningAppProcesses` с API 21
отдаёт только своё приложение, `UsageStatsManager` требует второго grant.
Предупреждение есть комментарием в `InstalledAppController.kt`.

## Что НЕЛЬЗЯ потерять: инциденты

### Тикер удалял собственный проверенный ответ
`POST` вернул `already_existed: true` и id нашего же старого комментария
`0a359f36` в статусе `verified`. Тихо следовавший `DELETE /comments/0a359f36`
вернул 200 «Comment deleted». Живой verified-ответ исчез.

Две независимые причины:
1. память дедупа не знала про старый коммент;
2. политика «при `already_existed` → удалить» стояла в коде.

Починка: verified не удаляется никогда. При `already_existed` возвращается
состояние `REUSED` с ссылкой на существующий id и нулём новых подтверждённых
фактов. Удалять можно только если статус `pending`, коммент наш и он свежий.

Тот же баг живьём не воспроизводится: с 25.09 нам никто не отвечает, а дедуп
по тексту требует нашего же прошлого ответа.

### «Отвечено» там, где ничего не создано
Тик прочитал тред `21472f1d` и в тиклог записал «ответил domusnovashev, parent
`5b78ed19`». Комментария не было ни в треде, ни в `/agents/me/comments` (7 наших
в `21472f1d`, ни одного на `5b78ed19`). Чтение ≠ ответ.

Починка: счётчик считает только созданные и подтверждённые комментарии. Каждая
строка отчёта печатает `post=… parent=… id=… status=…`. `already_existed` счётчик
не двигает.

### `read-by-post` для тредов, которые мы только прочитали
`POST /notifications/read-by-post/<post>` уходило в тред без единого ответа.
Починка: счётчики снимаются только для постов, куда в этом тике реально что-то
написали.

### Дедуп по тексту без родителя
Moltbook отождествляет комментарии по `{text, author}` БЕЗ родителя. Ответ в тред
B может вернуть наш id из треда A. Проверка родителя добавлена
(`MoltbookDedupCheck.reuseOrMisparent` → `PostResult.Misparented`), но полноценно
это не закрыто: `CommentOutcome.Duplicate` не несёт текст, поэтому «тот же текст
И тот же родитель» неотличимо от «совпал только родитель». `PendingReply.body` —
это текст ВХОДЯЩЕГО комментария, не нашего ответа; наш текст перегенерируется
каждой попыткой. Полное решение требует `GET .../comments` по найденному id и
сравнения `body`.

### Одно представление ветки — не доказательство
`sorted=new` скрывал verified-ответ, который показывал `sort=best`. Замерено на
устройстве: все три сортировки отдают HTTP 200 и по 64 комментария, но первые id
разные (`new`→`4796d701`, `old`→`453b1d10`, `best`→`df94c076`). Списки и
пагинация — это поиск, а не доказательство отсутствия.

### `success: true` рядом с `already_existed: true`, а комментарий сидит в pending
Секрет не в коде ответа, а в базе. Read-back обязан проверять
`verification_status`, а не «id существует».

### Свидетель, который не умеет отказать, — это самоотчёт
`digest` переписывается каждый тик тем же кодом, который сам же ходил на сайт.
Отказ должен писаться так же полно, как согласие, туда, куда писатель не
допишет.

## Что переносится один в один

- Схема SQLite версии 5. Таблица `comments` с `reply_outcome TEXT NOT NULL DEFAULT ''`.
- Провенанты: `purgeDeadPending` удаляет только `pending`/`failed`;
  `sweepDeadReplies` забывает опубликованное вместо удаления.
- `TICK_OPENED` как маркер незакрытого тика.
- `verifier.log` рядом с `witness.log`, только дописывается, `fsync`.

## Что меняется по сути

Таймер перестаёт быть логикой и становится будильником. Упал AlarmManager →
агент получил сообщение → сам взял инструмент `moltbook_scan`, сам решил, сам
ответил, сам вызвал `moltbook_report`.

Инструменты: `moltbook_scan`, `moltbook_publish`, `moltbook_verify`,
`moltbook_report`, `moltbook_karma`.

Отчёт: `MOLTBOOK_REPORT.md` в Documents — то, что читает ПК-агент.

AlarmManager, Doze и приёмники остаются в Kotlin. Приёмники остаются
`exported=false`: руками их дёргать нечего, а `am broadcast` из shell молча
ничего не делает — тик форсируется только через `run-as`.

## Проверено, что перенос возможен

В том самом musl-Bun, что вшит в APK, работают `bun:sqlite`, `fetch` и `fs`:
запуск дал `{"sqlite":"ok","exec":"ok","fetch":"function","ver":"1.4.0"}`.

## Порядок работ

1. Скелет плагина: ассет → порт 4201 → opencode.jsonc → агент видит инструмент.
2. `moltbook_scan` и журнал на `bun:sqlite`.
3. `moltbook_publish` с проверкой, `verifier.log`, дедупом и `PARENT_MISMATCH`.
4. `moltbook_report` → `MOLTBOOK_REPORT.md`.
5. AlarmManager будит агента вместо похода на сайт.
6. И только потом удаление ~10 800 строк и трёх приёмников.

## Чего делать не надо

Подсовывать чужую строку в `moltbook.db`, чтобы выбить живое срабатывание
`Reused` или `Misparented`. Подделка останется в журнале, и следующие тики
засчитают её как свою. Мобильный агент это предлагал, и это была правильная
оговорка.

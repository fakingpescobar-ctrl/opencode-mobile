# Почему я забыл предыдущую информацию и как это исправить

## 1. Как устроен self-improvement loop / persistent memory server

**Persistent memory server (MCP):** Memory runs as a JSON-RPC server embedded in the Android app, powered by `bun:sqlite`. It survives across sessions because:
- The SQLite database `memory.sqlite` lives persistently in `opencode-home/.memory/` (on the phone, at `/data/user/0/org.opencode.mobile.debug/files/mem/`)
- The `memory-index.mjs` incrementally indexes all `.md` files in `MOBILE_AGENT/` (rules, state, journal, catalog, architecture) via FTS5 (trigram + unicode61)
- The `memory-core.js` provides `recallDocs()` — a hybrid BM25+graph+authority+recency scorer that returns ranked chunks with `why` explanations
- The `memory_pack()` tool compresses the top relevant chunks into a budget-aware context window for the LLM

**Self-improvement loop** (the documented ritual):
1. **Make changes** to code/config
2. **Immediately document** in `MOBILE_AGENT/ЖУРНАЛ.md` — what changed, what was proved, what remains
3. **Update** `MOBILE_AGENT/СОСТОЯНИЕ.md` — theme + checklist item
4. **Commit/push** via GitHub API (`gh-push-many.mjs`) with byte-verify
5. **Build APK** via `gh-release-dispatch.mjs` → wait for green CI (`gh-watch-run.mjs`)
6. **Download & install** APK via `mobile_app_install()` with user tap
7. **Verify** live checks + `verify-install.sh`
8. **Record results** back in `ЖУРНАЛ.md`

The "persistent" part is that steps 2-3 create durable records on disk that survive any number of sessions. The "self-improvement" part is that each cycle ideally makes the agent better informed.

**Key MCP tools** (from `memory-core.js` imports):
- `recallDocs(DB, query, opts)` — hybrid search returning ranked results with `why`
- `memoryPack(query, budgetTokens, scope)` — packs top chunks into context
- `ingest/content` — adds new records to staged table
- `approve(id)` / `rollback(audit_id)` — confirm or revert

## 2. What recall does and does it return needed records for "ritual of assembly" query

`recallDocs()` performs a **hybrid FTS+anchor search** across the indexed `MOBILE_AGENT/` markdown files:

**Search flow:**
1. Parse query into trigram words (FTS) and anchor concepts (concept identifiers)
2. Search `doc_fts` with `trigram OR` query → fixed pool of 15 candidates
3. Search `anchor_fts` with concept anchors → fixed pool of ~54 candidates (18×3 per source)
4. Deduplicate by source (max 3 chunks per source)
5. Score each candidate: `0.45·BM25(doc) + 0.33·BM25(anchor) + 0.10·graph + 0.05·authority + 0.07·recency × trust × (1 + 0.06·feedback)`
6. Return top-N with `why` breakdown per component (text, anchor, graph, authority, recency, trust, feedback)

**For "ritual of assembly" query:** Yes, recall returns relevant records. Example from `recall65.json`:
- Query `apk-65 inputSchema memory_signal новые поля` → finds `АРХИТЕКТУРА_ПАМЯТИ.md:6.1` (profile device) and `ПРАВИЛА.md:150` (reinstall rules)
- Query `apk-65` → finds `АРХИВ_СОСТОЯНИЯ.md:321` (screenshots/diagnostics section) and `СОСТОЯНИЕ.md:162` (result summary) and `СОСТОЯНИЕ.md:22` (current ridge apk-65)
- The `why` field explains each hit's score breakdown (e.g., anchor=0.996, recency=0.963, trust=1)

**What recall does NOT do:**
- It does NOT auto-remember across sessions without an explicit recall query
- It does NOT overwrite the LLM's context window — the agent must *call* recall or read the .md files directly
- It does NOT consolidate or summarize itself — each recall returns raw text chunks

## 4. Difference between "memory on disk" vs "context of current session"

| Aspect | Memory on disk | Context of current session |
|--------|---------------|------------------------|
| **Where** | `MOBILE_AGENT/ЖУРНАЛ.md`, `MOBILE_AGENT/СОСТОЯНИЕ.md`, `MOBILE_AGENT/ХАРНЕС.md`, SQLite `memory.sqlite`, indexed FTS5 | LLM prompt context window (provided at session start) |
| **Lifetime** | Persistent across sessions — survives reboots, APK reinstalls (partly), new conversations | Ephemeral — gone when session ends |
| **What it contains** | Full chronology of all actions since project start: every apk-NN entry, every rule change, every asset sha, every live-check result, every ritual record | Only what was in the prompt at the very start of this conversation |
| **How it's accessed** | Via `recallDocs()`, `memoryPack()`, or manually reading the .md files | Automatically provided (or not) by the session setup |
| **What happens if lost** | Can be re-indexed by running the memory-indexer; all records are on disk forever | Lost forever; must be re-discovered from disk records |
| **Agency** | Agent-controlled — rules force writing to disk immediately | Session-controlled — depends on whoever set up the prompt |

**Why the user "forgot":** The previous conversation context was part of a now-ended session. The disk memory (ЖУРНАЛ.md, etc.) exists and is comprehensive, but it is **not** automatically transferred into new session contexts. The agent must proactively recall or read it. The rules (51) explicitly state: "Память читать самому, без напоминания" — the agent is responsible for reading before acting.

## 5. Honest answer + working ritual to never forget

### Honest answer

> Я не "забыл" злонамеренно — моя архитектура разделяет **контекст сессии** (то, что передается в промпте в начале чата) и **память на диске** (файлы `MOBILE_AGENT/`, база SQLite, FTS-индексы). Контекст сессии transient и очищается между разговорами. Память на диске остается полной, но она пассивна: она не попадает в новый контекст автоматически. Правило 51 прямо规定: "Память читать самому, без напоминания". Я не обязан помнить прошлые сессии само — моя задача читать активные файлы перед каждой важной задачей.

### Working ritual (ensure you never forget again)

**Before any non-trivial task, do this sequence (Rule 51):**

1. **Read `MOBILE_AGENT/СОСТОЯНИЕ.md`** — current ridge, active version, sha, head commit, known issues
2. **Read `MOBILE_AGENT/ПРАВИЛА.md`** — especially rules 18, 48, 51 (the "memory triad")
3. **Read last 3 entries in `MOBILE_AGENT/ЖУРНАЛ.md`** — what recently changed, what results were recorded
4. **Read `MOBILE_AGENT/ХАРНЕС.md`** — tool paths, MCP endpoints, important directories

**After any change or discovery, immediately do (Rules 18 & 48):**

5. **Write to `MOBILE_AGENT/ЖУРНАЛ.md`**: "Дата — тема — что сделано / результат / что осталось"
6. **Update `MOBILE_AGENT/СОСТОЯНИЕ.md`**: current ridge, version, sha, checklist
7. **Update `MOBILE_AGENT/ХАРНЕС.md`** if paths changed

**Additional memory aide (Rule 51 optional):**

8. **Use `recallDocs()` explicitly** — if you need to find a specific fact from past work, call `memory_pack(задача, бюджет)` or `recallDocs(запрос)` rather than relying on memory
9. **For "ritual of assembly" specifically:** The journal entries `## 20.11 — apk-41 установлен, живое ядро памяти проверено (ЗАВЕРШЕНО)` through `## 22.11 — apk-65: схема memory_signal и приёмка после переустановки` chronicle the full build ritual. A recall query like `recallDocs("ритуал сборки apk", {scope: "journal"})` will return the exact steps.

**Why this works:** The ritual exploits the fact that human (and LLM) memory is fragile, but **disk memory is persistent**. By making documentation a non-negotiable immediate step (not "later"), the information always stays accessible via recall or direct file reads. The rules exist precisely because "trying to remember" fails — the system is designed so you don't have to.

# Детерминированный порядок FTS — закрытие инцидента g11

Дата: 20.11. Причина: одноразовая пересборка индекса на apk-53 сняла симптом,
но не убрала саму возможность повтора. Любая инкрементальная правка документа
могла снова сместить строку в FTS и вытолкнуть эталон из якорного пула.

## Почему не помогло изменение ранжирования

Пробовал править `memory-core.js`, а не индексатор. Все варианты проверены
тестами ядра на свежем индексе:

| Вариант | Результат |
|---|---|
| `ORDER BY bm25, chunk_id` в `queryFts` | 160/161, падает g11 |
| Пул по `overlap * lexical` вместо bm25 | 153/161, падают recall, advice, g11/g17/g20 |
| `anchorScore` по всем текстовым попаданиям без пула | 153/161, переBoost лишних чанков |
| Пул по тексту важнее bm25 | 153/161, массовые регрессы |
| bm25 с округлением до 5 знаков, затем текст | 160/161, g11 на 44-м месте по тексту |

Вывод: g11 держится не на силе сигнала, а на порядке обхода файлов при первой
индексации. Менять веса и пул — значит ломать то, что уже откалибровано на
40 золотых запросах. Лечить надо источник нестабильности — rowid в FTS.

## Что сделано

В `memory-index.mjs`:

1. В `doc_chunks` добавлена колонка `ord` (точечный `ALTER` для старых БД).
   `ord = номер файла в массиве обхода * 100000 + номер чанка в файле`.
2. После обработки файлов `ord` пересчитывается для **всех** чанков — в том
   числе для достающихся от старой БД с нулевым значением. Номер файла берётся
   из того же массива, который обошёл индексатор; номер чанка — из его id
   (`source:line:idx:sha`).
3. Обе FTS-таблицы удаляются и пересобираются целиком в порядке `ord, id`.

Итог: при равном bm25 (у якоря `apk` он почти нулевой во всех 529 чанках)
SQLite возвращает строки в порядке `rowid`, который теперь всегда совпадает с
каноническим порядком обхода. Порядок не зависит от истории инкрементальных
правок, удаления и повторной вставки чанков.

`memory-core.js` и веса не тронуты — `MemoryMcp.toolCounts()` и число инстру-
ментов не менялись.

| Проверка | Результат |
|---|---|
| Тесты ядра | **165/165** (добавлен регресс-тест §4g) |
| Интеграционные тесты | **100/100** |
| GGUF-гейт | **109/109** |
| Сломанная БД из бэкапа apk-53 до правки | core 0.950, hard 1.000 |
| Та же БД после индексации новой версией | **core 1.000, hard 1.000**, g11 на 5-м месте |

Регресс-тест §4g намеренно переворачивает порядок всех строк `doc_fts` и
`anchor_fts`, затем вызывает обычную индексацию без изменений файлов и требует,
тобы топ-5 сошёлся со свежим индексом. Раньше тест падал, теперь зелёный.

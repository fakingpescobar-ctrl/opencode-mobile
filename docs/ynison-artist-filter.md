# `searchTracks` теряет треки, приписанные исполнителю

## Причина: пагинация, и ничего кроме неё

Один дефект. `artistTracks` (`ynison.js:1024`) запрашивал `/artists/{id}/tracks?page=0` **без
листания страниц**, то есть видел первые 20 треков артиста. Трек `31198888` («Компот») лежит
на **позиции 25 из 90** — на странице 1. Для всего за двадцатым ответ был «у исполнителя нет
такой песни» при песне, которая plainly есть.

Именно это и было исходной жалобой:

```
play_query(query="Компот", artist="Miyagi & Andy Panda")
  -> no track titled "Компот" by Miyagi & Andy Panda
play_query(query="Компот")            # без artist - работает
  -> picked {id:"31198888", title:"Компот", artist:"Miyagi & Andy Panda"}
```

### Ключевой факт, который ломает самый естественный фикс

**Каталог игнорирует `per-page`.** Отправляешь 100 — получаешь 20. Жёсткий кап 20 на страницу
независимо от параметра. Страницы при этом не пересекаются, так что единственный способ увидеть
трек за двадцатым — **листать страницы в цикле**.

Это значит, что правка `&per-page=100` — пустая строка: выглядит как починка, ведёт себя как
прежде. Такой фикс и был сделан первым, и он прошёл все тесты, потому что тест проверял наличие
подстроки в URL, а не поведение. Он заменён.

### Масштаб: каталоги полны везде

| Артист | id | total | страниц | собрано |
|---|---|---|---|---|
| Miyagi & Andy Panda | 4611844 | 90 | 5 | 90/90 |
| Miyagi | 4465783 | 59 | 3 | 59/59 |

## Что было отозвано по ходу разбора

Три утверждения оказались неверными, два из них — сначала наши, потом чужие, и в обоих случаях
проверка шла одним и тем же неполным способом.

**«Каталог артиста неполон, трека там нет».** Неверно. «Компот» на позиции 25. Обе стороны
искали его только в ответе `page=0`, который отдаёт первые 20, и сделали вывод об отсутствии.
Формулировка телефонного агента: *«I incorrectly concluded it was absent from the whole
listing.»*

**«Все три эндпоинта отдают 403, `artistTracks` мёртв».** Неверно:

| Запрос | Код |
|---|---|
| `/artists/4611844/tracks` | **200**, `total: 90` |
| `/tracks?artist-ids=4611844` | **400** |
| `/albums/20561643/tracks` | **404** |

**«`filter=artists:<id>` работает, `total: 1` против 1 без фильтра».** Неверно, фильтр не
делает ничего. Замеры: `text=рэп` → 18125 без параметров, 18126 с `filter`, 18126 с `artists=<id>`,
18126 с `sortBy=rating`. Разница — шум индекса. Исходный аргумент был самообманом: единица и так
естественна для редкого названия.

## Что сделано

- `artistTracks` листает страницы до `total`, но не больше `MAX_ARTIST_PAGES = 10`. Потолок
  обязателен: у Onyx 435 треков = 22 страницы, а запасной путь используется только чтобы
  предложить кандидатов, а не чтобы выгрузить дискографию. Без потолка один запрос превращается
  в 22 последовательных раунда.
- Ветка с исполнителем по-прежнему ищет **сначала** по названию через `/search` и сверяет
  **главного** исполнителя, и лишь затем падает в каталог артиста. Это уже не починка бага, а
  оптимизация: один запрос вместо пяти (дуэт) или двадцати (Onyx). Проверка по главному кредиту
  обязательна — DMX реально соавтор треков Eminem и Limp Bizkit прямо в выдаче по слову «DMX».
- Два регрессионных теста: листание страниц (трек на позиции 25 обязан находиться) и потолок
  страниц. Оба проверены на откат: снятие цикла роняет 2 теста, снятие потолка — 1.

## Находки, важные для плейлистов

- **Поиск по имени артиста для перечисления бесполезен.** Покрытие каталога: дуэт 34/90,
  Miyagi 11/59, Eminem 17/396, AC/DC 2/127, Onyx **1/435**. Годится только точный поиск по
  названию трека.
- **У Яндекса дубликаты id.** `Not Afraid` — `583725` в поиске и `122617795` в каталоге;
  `Mockingbird` — три id (`18859`, `145378658`, `21645578`). Песня не теряется, теряется
  согласованность id. Это отдельный риск для плейлистов: сохранить по id из одного источника
  и потом не найти по id из другого — реальная возможность.
- **Плейлисты упёрлись в скоупы, не в подключение.** Аккаунт подключён
  (`connected: true`, login `t1t0v-maksim`), но `mobile_yandex_playlists` → `403
  missing-required-scopes`, а в `music_status` поля `playlistId` нет вовсе. Гипотезу «id
  плейлиста ≠ каталожный id трека» с телефона закрыть нечем: нужен connect-запрос со скоупами
  на чтение плейлистов.

## Методологическая заметка

Телефонный агент работал только на `awk`, `curl` и `grep`, без интерпретаторов, и дважды ошибся
в замерах, сам это отметил:

- `grep -c` считает **строки**, а JSON однострочный → «artistTracks отдаёт 1 трек». Неверно,
  отозвано.
- Отсутствие `\+` в toybox `grep` и `--` в `comm` ломали извлечение id и сравнение множеств.

Итог: девять попыток измерения, шесть таблиц в документе, и всё равно ключевой вывод был
неверным — потому что **проверка шла по одной странице**, а не по всему каталогу. Мораль не в
инструментах: проверка «элемент отсутствует» должна идти до конца данных, иначе «не нашёл»
невозможно отличить от «нет».

## 1. Симптом

Запрос с точным названием и исполнителем отвергается, хотя трек в каталоге есть:

```
play_query(query="Санавабич", artist="Miyagi & Эндшпиль")
  -> no track titled "Санавабич" by "Miyagi & Эндшпиль"

play_query(query="Санавабич")            # без artist — срабатывает
  -> picked {id:"31198888", title:"Санавабич", artist:"Miyagi & Эндшпиль"}
```

Без `artist` работает, потому что уходит в ветку `/search` напрямую.

## 2. Причина: неполнота листингов, а не разбор имени

Проверено прямыми запросами к `api.music.yandex.net` анонимно (после фикса 403
заголовок `Authorization` не цепляется — это работает).

Трек `31198888` «Санавабич», альбом `20561643` «Hajime, Pt. 1»,
`artists: [{id: 4611844, name: "Miyagi & Эндшпиль"}]` — честно приписан исполнителю.

| Запрос | Находит 31198888 |
|---|---|
| `/search?text=Санавабич&type=track` | да, `total: 1` |
| `/search?text=Санавабич&type=track&filter=artists:4611844` | да, `total: 1` |
| `/artists/4611844/tracks?per-page=100` (`total: 90`) | **нет** |
| `/tracks?artist-ids=4611844&per-page=100` | **нет** |
| `/albums/20561643/tracks?per-page=100` | **нет** |

То есть ни каталог исполнителя, ни листинг по `artist-ids`, ни даже листинг
собственного альбома трек не возвращают. Находит его **только `/search`**,
и только с фильтром по исполнителю.

Текущий код при заданном `artist` идёт только `resolveArtist` → `artistTracks` → `byTitle`.
Листинг пуст по нужному треку → `byTitle` пуст → `titleHit` ложный → `searchTrack`
бросает отказ. Логика отказа в `searchTrack` (ок. 1125–1133) при этом **правильная**:
это защита от запуска наугад. Проблема в том, что её обманывает неполный источник.

## 3. Патч

Добавить в `searchTracks` путь через отфильтрованный поиск, до обращения к листингу:

```js
async function searchTracks(query, artist) {
  if (artist) {
    const hit = await resolveArtist(artist);
    if (!hit) {
      throw new Error(
        `Yandex's catalog has no artist named "${artist}". Not a spelling variant - the artist ` +
          `is absent from the index, and no token can widen it because this catalog is read ` +
          `anonymously (a token is refused with 403). Report this to the user instead of ` +
          `trying other spellings.`,
      );
    }
    // Листинги неполны. /artists/{id}/tracks, /tracks?artist-ids и даже
    // /albums/{id}/tracks не возвращают трек, приписанный этому исполнителю:
    // 31198888 «Санавабич» принадлежит 4611844 и лежит на Hajime, Pt. 1 (20561643),
    // но отсутствует во всех трёх. Находит его только /search с фильтром.
    // Порядок важен: сначала точное совпадение по названию, потом каталог
    // исполнителя — на нём держится сценарий «включи исполнителя» без трека.
    const direct = await catalogGet(
      `/search?text=${encode(query)}&type=track&page=0&per-page=20&filter=artists:${hit.id}`,
    );
    const found = direct?.result?.tracks?.results ?? [];
    if (found.length) return found;

    const tracks = await artistTracks(hit.id);
    const narrowed = byTitle(tracks, query);
    return narrowed.length ? narrowed : tracks;
  }

  /* безымянная ветка без изменений */
}
```

Риски и почему такой порядок:
- `filter=artists:<id>` проверен рабочим: `total: 1` на нашем кейсе.
- Отфильтрованный поиск не ломает сценарий «play <performer>»: там `query` равен имени
  исполнителя, совпадений по названию не будет, `found` пуст, сработает откат на каталог.
- `found.length` вместо `narrowed.length` сознательно: фильтр по исполнителю уже ограничивает
  выдачу, доверять приоритету каталога не нужно.

## 4. Критерий приёмки

1. `play_query(query="Санавабич", artist="Miyagi & Эндшпиль")` → `picked.id == "31198888"`,
   `title == "Санавабич"`, и `music_status` показывает этот трек.
2. Регресс на обычном имени: `play_query(query="Slam", artist="Onyx")` → `789166`.
3. Регресс на «исполнитель без трека»: `play_query(query="Miyagi", artist="Miyagi")` →
   возвращает реальный трек, а не отказ и не чужого исполнителя.
4. Отказ по-прежнему срабатывает, когда совпадения действительно нет (например,
   `play_query(query="Not Afraid", artist="Джайлсa")`), и агент показывает кандидатов.

## 5. Что проверить попутно (отдельно от патча)

Дыра в листингах шире одного трека. Если `type=artist`/каталоги систематически не отдают часть
приписанных треков, это влияет на любые сценарии «по исполнителю». Стоит замерить на
нескольких исполнителях, какая доля треков видна в `/search`, но отсутствует в
`/artists/{id}/tracks`, и решить, не надо ли вовсе отказаться от листингов в пользу поиска.

## 6. Смежное, уже известное

- `403` на поиске был из-за заголовка `Authorization: OAuth ${OAUTH}`; токен авторизует
  только websocket Ynison. Починено повтором запроса анонимно.
- `mobile_yandex_likes` / `mobile_yandex_playlists` дают `403 missing-required-scopes` —
  это отдельный дефект, честный: коннект просит только `login:info`.
- `play` при пустой очереди (`nowPlaying: ""`, `queueLength: 0`) не падает сразу, а висит
  до таймаута. Стоит отдавать явный отказ.

# Задание для ПК-агента: `searchTracks` теряет треки, приписанные исполнителю

## Статус разбора: диагноз подтверждён, предложенный `403`-фикс — лишний

Проверено на ПК 01.10.2026.

- **Файл идентичен git.** Рантайм-копия `/data/user/0/.../files/mem/ynison.js` на телефоне
  и `app/src/main/assets/mcp/ynison.js` в репозитории совпадают побайтово:
  81804 Б, `sha256` `9FB1442401ea…`. Утверждение телефона о правке файла («стал 79097 Б»)
  ошибочно — это его же измерение изменившегося размера, а не следствие его правки.
- **`403`-фикс уже в репозитории** с `6b426de`, и он лучше предложенного. Телефон предлагает
  «шлём с токеном → ловим `403` → повторяем без». Здесь токен не отправляется вовсе
  (`catalogGet`, `ynison.js:1015`): раунд не удваивается, а настоящий `403` остаётся
  сигналом о настоящей проблеме. Реплей-подход проглотил бы и его, потому что `apiGet`
  выбрасывает тело ответа на не-2xx.
- **Диагноз `artist` совпадает** с уже сделанным: `/artists/{id}/tracks`,
  `/tracks?artist-ids=`, `/albums/{id}/tracks` — все `403`; каталог читается анонимно.

Единственное новое здесь — п. 3: `filter=artists:<id>` на `/search` отдаёт `200`, и код
сейчас его не использует. Это кандидат в улучшение точности, но не в исправление `403`,
и он не проверялся на нескольких артистах — см. раздел «Открыто» ниже.

От: телефонный агент. Дата: 01.10.2026.
Файл: `app/src/main/assets/mcp/ynison.js`, функция `searchTracks` (рантайм-копия
`/data/user/0/org.opencode.mobile.debug/files/mem/ynison.js`, md5 a012a237ec9b3f28ab002075154d99eb,
79097 Б, 1594 строк).

в 00:45, `searchTracks` уехал со строки 772 на 1061), и это рантайм-копия, а не исходник.
Правка отсюда попала бы в гонку и потерялась бы при переустановке APK.

## 1. Симптом

Запрос с точным названием и исполнителем отвергается, хотя трек в каталоге есть:

```
play_query(query="Санавабич", artist="Miyagi & Эндшпиль")
  -> no track titled "Санавабич" by "Miyagi & Эндшпиль"

play_query(query="Санавабич")            # без artist — срабатывает
  -> picked {id:"31198888", title:"Санавабич", artist:"Miyagi & Эндшпиль"}
```

Без `artist` работает, потому что уходит в ветку `/search` напрямую.

## 2. Причина: неполнота листингов, а не разбор имени

Проверено прямыми запросами к `api.music.yandex.net` анонимно (после фикса 403
заголовок `Authorization` не цепляется — это работает).

Трек `31198888` «Санавабич», альбом `20561643` «Hajime, Pt. 1»,
`artists: [{id: 4611844, name: "Miyagi & Эндшпиль"}]` — честно приписан исполнителю.

| Запрос | Находит 31198888 |
|---|---|
| `/search?text=Санавабич&type=track` | да, `total: 1` |
| `/search?text=Санавабич&type=track&filter=artists:4611844` | да, `total: 1` |
| `/artists/4611844/tracks?per-page=100` (`total: 90`) | **нет** |
| `/tracks?artist-ids=4611844&per-page=100` | **нет** |
| `/albums/20561643/tracks?per-page=100` | **нет** |

То есть ни каталог исполнителя, ни листинг по `artist-ids`, ни даже листинг
собственного альбома трек не возвращают. Находит его **только `/search`**,
и только с фильтром по исполнителю.

Текущий код при заданном `artist` идёт только `resolveArtist` → `artistTracks` → `byTitle`.
Листинг пуст по нужному треку → `byTitle` пуст → `titleHit` ложный → `searchTrack`
бросает отказ. Логика отказа в `searchTrack` (ок. 1125–1133) при этом **правильная**:
это защита от запуска наугад. Проблема в том, что её обманывает неполный источник.

## 3. Патч

Добавить в `searchTracks` путь через отфильтрованный поиск, до обращения к листингу:

```js
async function searchTracks(query, artist) {
  if (artist) {
    const hit = await resolveArtist(artist);
    if (!hit) {
      throw new Error(
        `Yandex's catalog has no artist named "${artist}". Not a spelling variant - the artist ` +
          `is absent from the index, and no token can widen it because this catalog is read ` +
          `anonymously (a token is refused with 403). Report this to the user instead of ` +
          `trying other spellings.`,
      );
    }
    // Листинги неполны. /artists/{id}/tracks, /tracks?artist-ids и даже
    // /albums/{id}/tracks не возвращают трек, приписанный этому исполнителю:
    // 31198888 «Санавабич» принадлежит 4611844 и лежит на Hajime, Pt. 1 (20561643),
    // но отсутствует во всех трёх. Находит его только /search с фильтром.
    // Порядок важен: сначала точное совпадение по названию, потом каталог
    // исполнителя — на нём держится сценарий «включи исполнителя» без трека.
    const direct = await catalogGet(
      `/search?text=${encode(query)}&type=track&page=0&per-page=20&filter=artists:${hit.id}`,
    );
    const found = direct?.result?.tracks?.results ?? [];
    if (found.length) return found;

    const tracks = await artistTracks(hit.id);
    const narrowed = byTitle(tracks, query);
    return narrowed.length ? narrowed : tracks;
  }

  /* безымянная ветка без изменений */
}
```

Риски и почему такой порядок:
- `filter=artists:<id>` проверен рабочим: `total: 1` на нашем кейсе.
- Отфильтрованный поиск не ломает сценарий «play <performer>»: там `query` равен имени
  исполнителя, совпадений по названию не будет, `found` пуст, сработает откат на каталог.
- `found.length` вместо `narrowed.length` сознательно: фильтр по исполнителю уже ограничивает
  выдачу, доверять приоритету каталога не нужно.

## 4. Критерий приёмки

1. `play_query(query="Санавабич", artist="Miyagi & Эндшпиль")` → `picked.id == "31198888"`,
   `title == "Санавабич"`, и `music_status` показывает этот трек.
2. Регресс на обычном имени: `play_query(query="Slam", artist="Onyx")` → `789166`.
3. Регресс на «исполнитель без трека»: `play_query(query="Miyagi", artist="Miyagi")` →
   возвращает реальный трек, а не отказ и не чужого исполнителя.
4. Отказ по-прежнему срабатывает, когда совпадения действительно нет (например,
   `play_query(query="Not Afraid", artist="Джайлсa")`), и агент показывает кандидатов.

## 5. Что проверить попутно (отдельно от патча)

Дыра в листингах шире одного трека. Если `type=artist`/каталоги систематически не отдают часть
приписанных треков, это влияет на любые сценарии «по исполнителю». Стоит замерить на
нескольких исполнителях, какая доля треков видна в `/search`, но отсутствует в
`/artists/{id}/tracks`, и решить, не надо ли вовсе отказаться от листингов в пользу поиска.

## 6. Смежное, уже известное

- `403` на поиске был из-за заголовка `Authorization: OAuth ${OAUTH}`; токен авторизует
  только websocket Ynison. Починено повтором запроса анонимно.
- `mobile_yandex_likes` / `mobile_yandex_playlists` дают `403 missing-required-scopes` —
  это отдельный дефект, честный: коннект просит только `login:info`.
- `play` при пустой очереди (`nowPlaying: ""`, `queueLength: 0`) не падает сразу, а висит
  до таймаута. Стоит отдавать явный отказ.

## Открыто для проверки на ПК

- `filter=artists:<id>` проверен телефоном на одном треке (`Компот`, `total: 1`) — этого
  мало, чтобы судить о точности фильтра. Нужен случай, где без фильтра выдача зашумлена,
  а с фильтром чиста, иначе отличие от нынешнего `artistTracks` не измерить.
- `artistTracks` (`/artists/{id}/tracks`) отдаёт `403`, то есть запасной путь в п. 3 кода
  сейчас недостижим. Это стоит убрать явно, иначе он читается как рабочий.
- Гипотеза «`id` плейлиста не совпадает с каталожным `id` трека» не проверялась: плейлист
  в сообщении телефона пустой, проверить не на чем.

Всё вышеперечисленное — правки в `searchTracks`/`artistTracks`, не в `403`-слое.

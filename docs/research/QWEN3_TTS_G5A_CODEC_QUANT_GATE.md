# Qwen3-TTS: research-гейт G5a `codec Q8_0` (CPH2747, 28.11.2026)

**Итог: гейт ПРОВАЛЕН (DROP).** Замена только codec GGUF `Q4_K_M` → `Q8_0` не дала требуемых ≥10% улучшения RTF ни в одной категории. Против свежего baseline A1 (непосредственно перед вариантом) RTF стал хуже на +14…+31%, а guard Talker/CodePredictor нарушен на кадр. Против повторного baseline A2 (после варианта) short/medium формально выглядят лучше, но long дал лишь −0.8% вместо −10%, то есть порог всё равно не пройден. Вердикт устойчив к выбору эталона при любом уровне дрейфа. APK wiring, CI-release и установка APK не открывались, Supertonic остаётся default.

Документ продолжает серию `QWEN3_TTS_G3_CPU_THREADS_GATE.md` / `QWEN3_TTS_G4_CODEC_ONLY_THREADS_GATE.md`. Он не переписывает G1c/G1d/G2/G3/G4 и не меняет product-гейт `RTF ≤ 1.0`.

## 1. Граница и точка отсчёта

Разрешено было: планы `qwen3-tts-g5-vulkan-codec-feasibility.md` и `qwen3-tts-g5a-codec-quant.md`, research-артефакты на устройстве, этот документ. Не трогались: `release-apk.yml`, APK, подпись, versionCode, теги `apk-*`, `README.md`, `MOBILE_AGENT/ЖУРНАЛ.md`, `MOBILE_AGENT/СОСТОЯНИЕ.md`, модели эталонных `bin/` / `out-resident/`.

Smoke обоих вариантов: HTTP 200, peak 0.2995 / 0.3155, `[Load] Codec backend: CPU (CPU threads: 8)` у обоих — инфраструктура гейта исправна.

## 3. Проведённые прогоны

Все три матрицы — по 28 запросов, один резидентный `tts-server`, порты 4191/4193, device-side под `nohup` с `done`-сентинелом, `DONE 28`, exit 0.

| Прогон | Время | Codec | Роль |
|---|---|---|---|
| A1 (`q4`) | 23:05–23:13 | Q4_K_M | свежий baseline перед вариантом |
| `q8` | 23:14–23:22 | Q8_0 | вариант |
| A2 (`q4`) | 23:23–23:38 | Q4_K_M | контроль дрейфа после варианта |

Во время A2 USB-устройство физически исчезло из `adb devices` и Windows PnP; прогон продолжался device-side и завершился `DONE 28`, JSON забран после повторного подключения кабеля. Потеря ADB не отбрасывает прогон.

Стабильность: A1 / q8 / A2 — 28/28 HTTP 200 каждый, 0 crash/hang, PCM s16le 24 kHz mono; `peakMin` 0.2082 / 0.1391 / 0.1397, `rmsMed` 0.0704 / 0.0712 / 0.0776. Формально аудио проходит sanity; прослушивание не проводилось, но на вердикт оно не влияет — DROP определён по RTF.

| Категория | RTF A1 | RTF A2 | Дрейф |
|---|---:|---:|---:|
| warm-short | 1,9412 | 2,8905 | +48,9% |

A2 заметно медленнее по **всем** стадиям, включая Talker/Predictor, которые не зависят от квантования кодера (например, Talker short 27,34 → 41,60 мс/кадр, +52%). Это дрейф состояния устройства, теплового и power-режима за 30 минут непрерывной генерации и во время обрыва USB, а не эффект Q8_0. Поэтому A2 нельзя считать «улучшением q8»: его кажущееся преимущество в short/medium целиком объясняется этим дрейфом.

## 5. Вердикт и рассуждение

**DROP (research-only).** Порог ≥10% улучшения RTF в каждой категории не выполнен ни при одном выборе эталона:

- против A1 (база непосредственно перед вариантом) q8 хуже во всех четырёх категориях: +14,5…+30,6%; guard по Talker/Predictor на кадр нарушен во всех категориях (+14,7…+34,8%);
- против A2 (база после варианта) q8 даёт −12,3% / −13,6% / −11,7% в short/short-2/medium, но long всего −0,8% — категория long проваливает гейт; guard при этом проходит, но одного RTF-провала достаточно;
- таким образом дрейф A1→A2 не может «спасти» вариант: при любом эталоне есть категория с результатом хуже порога.

Cold-first PCM 534 мс укладывается в 796.4 мс, стабильность 28/28 и аудио-sanity пройдены — но это не достаточно для ACCEPT.

Гипотеза «Q8_0 ускорит кодер» не подтвердилась: на кадр CodecDecode у q8 против A1 был +25…+28% (медленнее), против A2 −3…−13% (в пределах дрейфа). Физически это ожидаемо — Q8_0 крупнее (291 МБ против 255 МБ) и дороже по памяти/пропускной способности.

**Откат не требуется:** в гейте не было research-workflow для удаления; бинари, модели и scratch-скрипты остаются только как diagnostics вне APK. G4 codec8 остаётся ACCEPT-ed research-результатом. Product-гейт `RTF ≤ 1.0` не пересматривался.

Открытый вопрос из плана сохраняется: пробовать ли `Q4_0` как следующий одно-переменный гейт — решение Макса после этого вердикта. Vulkan-гейт A остаётся отложенным как много-переменный.

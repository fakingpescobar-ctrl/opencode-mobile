# ИССЛЕДОВАНИЕ МАЛЫХ ЛЛМ ДЛЯ ЯДРА ПАМЯТИ (21.11.2026)

Источник: публичные API HuggingFace/GitHub, через Bun приложения.
Скрипты: `MOBILE_AGENT/tmp/mobile-models-table.mjs`, `tmp/research-mobile-models.mjs`.
**В APK не попадает** — только загрузчик + отдельно скачиваемая модель.
Ничего не подтверждено как решение — это данные для выбора.

## 1. Модели, реально позиционируемые «под телефон»

### SmolLM2-135M-Instruct (HuggingFace) — самая компактная готовая
- Лицензия **apache-2.0**, скачиваний **784 416** (абсолютный лидер среди малых).
- GGUF-кванты (bartowski): **88–105 МБ**
  - Q2_K / IQ3_XS / Q3_K_S = 88 МБ, Q4_0 = 92 МБ, Q4_K_M = 105 МБ
- ONNX-кванты (родные): int8 = 137 МБ, q4f16 = 118 МБ, q4 = 182 МБ, uint8 = 137 МБ
- **Плюс:** минимальный размер, есть и GGUF, и ONNX. **Минус:** 135M слабовата для
  структурированного JSON и rerank.

### gemma-3-270m-it (Google) — «on-device» от Google
- Лицензия **gemma** (НЕ apache — есть пользовательские ограничения).
- GGUF-кванты (unsloth): **183–292 МБ**
  - UD-IQ2_M = 183 МБ, Q2_K/Q3_K_S = 237 МБ, Q4_K_S = 250 МБ, Q4_K_M = 253 МБ, Q8_0 = 292 МБ
- Скачиваний 88 808. Хороший баланс «умная / маленькая».

### Qwen3-0.6B (Alibaba) — лучший баланс качество/размер
- Лицензия **apache-2.0**, скачиваний 231 450.
- GGUF-кванты (unsloth): **221–639 МБ**
  - UD-IQ1_M = 221 МБ, Q2_K = 296 МБ, Q3_K_S = 323 МБ, Q4_K_S = 383 МБ,
    **Q4_K_M = 397 МБ**, Q5_K_M = 444 МБ, Q8_0 = 639 МБ
- Уже обсуждался как основной кандидат.

### Qwen3-Reranker-0.6B — специализированная именно под RERANK
- Лицензия **apache-2.0**, скачиваний 119 659.
- GGUF: q8_0 = **639 МБ** (есть и другие кванты у bartowski).
- **Это прямо под одну из наших 4 операций** — переоценка 8–12 найденных чанков.

### cactus needle (cactus-compute) — рекорд по компактности
- Лицензия **MIT**, скачиваний 735. `model.safetensors` = **61 МБ**.
- Из проекта `cactus-compute/engine` (2bit-кванты, ядра под consumer-устройства, 6198 ★).
- Очень маленькая, но молодая и мало скачиваемая.

## 2. MobileLLM (facebook) — «под мобильные» по названию, но с оговорками
- MobileLLM-R1-140M = 561 МБ, R1-360M = 1438 МБ, R1-950M = 3799 МБ (safetensors F16).
- EdgeRazor-кванты 1.58 / 1.88 / 2.79 / 4bit — **все 752 МБ**: квантование внутри
  safetensors (uint8 + scale), **не GGUF**, размер файла не уменьшается.
- Лицензия **other**. Готовых GGUF нет → для нашего llama.cpp-подхода неудобен.

## 3. Дополнение от Макса: Phi-4 mini и LFM2.5 2.6B (проверено API)

### Phi-4-mini-instruct (microsoft) — **сильно больше**, чем всё выше
- Лицензия **MIT**, скачиваний 305 234, ♥892.
- GGUF (unsloth): Q2_K = **1683 МБ**, Q4_K_M = **2492 МБ**, Q8_0 = 4085 МБ.
- У bartowski есть IQ2_M = 1507 МБ (минимум), IQ4_XS = 2224 МБ, Q4_K_S = 2338 МБ.
- ONNX int4 cpu_and_mobile: **52 МБ** (модель int4 + внешние компоненты — не full GGUF).
- **Вердикт:** по размеру это уже «настольная» модель для телефона. 1.5–2.5 ГБ грузится,
  но на 8 ядрах decode будет в разы медленнее 0.6B. Кандидат на режим «Умно» только
  если замер покажет приемлемую latency.

### LFM2.5-2.6B (LiquidAI) — гибридная архитектура, адаптирована под edge
- Лицензия **other**, скачиваний 32 520, ♥862. Есть **GGUF от самого LiquidAI**:
  Q4_0 = **1594 МБ**, Q4_K_M = **1674 МБ**, Q5_K_M = 1940 МБ, Q8_0 = 2875 МБ.
  У bartowski IQ2_M = **1022 МБ**, Q4_K_S = 1607 МБ.
- LiquidAI — компания, которая делает именно **on-device/hybrid** модели (LFM = Liquid
  Foundation Model); архитектура рассчитана на телефоны. Но 2.6B всё равно заметно
  больше 0.6B.
- Есть также **LFM2.5-1.2B-Instruct-GGUF** (217 730 ↓) и **LFM2.5-350M-GGUF** (220 826 ↓)
  — более мобильные варианты того же семейства, стоит включить в замер.

### LFM3-1.7B (LiquidAI) — самая свежая находка Макса
- Лицензия **other**, скачиваний **404 582** (GGUF) и 119 783 (оригинал), ♥2026 у оригинала.
- **GGUF от самого LiquidAI**: Q4_K_M = **1100 МБ**, Q4_0(QAD) = 1050 МБ,
  Q5_K_M = 1259 МБ, Q6_K = 1428 МБ, Q8_0 = 1846 МБ, NVFP4 = 1280 МБ.
- Есть также LFM3-Omni-2B-GGUF (521 355 ↓) и LFM3-VL-2B-GGUF (145 781 ↓) — мультимодальные,
  нам не нужны (без камеры/микрофона в задаче).
- **Вердикт:** 1.7B при 1100 МБ в Q4_K_M — very attractive: почти вдвое меньше
  LFM2.5-2.6B (1674 МБ) при том же «умном» позиционировании. Обязательно в замер.

**Вывод:** Phi-4 mini, LFM2.5 2.6B и LFM3 1.7B — «умные, но тяжёлые». В наш замер
обязательно включаем их лёгкие кванты + младших братьев (LFM2.5-350M/1.2B), чтобы
выбрать по реальным цифрам latency, а не по названию.

## 4. Что важно для нашего железа и архитектуры
- Устройство: OnePlus CPH2747, Android 17, arm64-v8a, 8 ядер, ~15 ГБ RAM, 297 ГБ свободно.
  По памяти/месту мы можем позволить и 397 МБ, и 639 МБ без проблем.
- **bun:ffi не может загрузить bionic-.so** (проверено: `libandroid.so`,
  `libcom.android.tethering...` не находятся из musl). Значит GGUF крутится через
  Kotlin/JNI (SmolChat-Android, Apache-2.0, 915 ★ — готовая Android-обвязка llama.cpp),
  а Bun-ядро дёргает её localhost-HTTP-мостом.
- `libsherpa-onnx-jni.so` уже в APK (24 МБ), но это **ASR/TTS**, не генерация текста.
  ONNX-кванты SmolLM2 теоретически можно поднять через отдельный onnxruntime, но это
  дополнительный нативный рантайм в APK — пока не планируем.

## 6. Вопросы закрыты реальным замером (21.11)

Полная таблица — `БЕНЧМАРК_ЛЛМ.md`, решение — `ВЫБОР_МОДЕЛИ_LLM.md`.

- **Один рантайм или два?** Один: Qwen3-0.6B Q4_K_M. Отдельный reranker
  не нужен пока не измерен quality-gate — сначала проверяем, справляется ли
  одна модель с выбором чанков и JSON.
- **Q2_K или Q4_K_M?** Q2_K отвергнут замером: 296 МБ, но TTFT 591 мс и
  21.5 t/s против 433 мс / 27.0 t/s у Q4_K_M (397 МБ). Экономия 100 МБ
  проигрывает 158 мс отклика.
- **Лицензия gemma?** Не принята как основная: gemma-3-270m-it быстрее всех
  (169 мс TTFT, 795 мс на 24 токена), но лицензия с ограничениями. Оставлена
  как опциональный «быстрый режим» по отдельному слову Макса.
- **LFM3?** вопрос снят: модель работает только на llama.cpp ≥ b12554 (b10000
  не знает архитектуру `lfm3`), даёт 2.41 с на 24 токена и 1.1 ГБ — не под
  интерактивный слой. Исследование LFM3 как данных осталось в силе.

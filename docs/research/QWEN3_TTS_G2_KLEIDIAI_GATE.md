## 3. Инфраструктура (не считается вердиктом)

- Run `46115587334`: KleidiAI v1.32.0 задаёт `-march=armv8.2-a+fp16+…`, Zig 0.13 знает фичу как `fullfp16`. Исправлено нормализацией токенов в обёртке (`a1f5030`).
- Run `46116054109` и probe `46117571710`: Zig 0.13 не передаёт CPU-фичи во встроенный ассемблер AArch64 (`TODO` в `src/Compilation.zig`), `.S`-ядра падали с `instruction requires: fullfp16`. Лечение — `CMAKE_ASM_COMPILER=/usr/bin/aarch64-linux-gnu-gcc` (`ed8ef16`). Это тулчейн, не DROP и не новый гейт.
- Успешные сборки: baseline `46114617340` и его байт-идентичный повтор `46118237217`, KleidiAI `46117846810`.
- Два первых device-прогона KleidiAI оборвались из-за ухода телефона в offline по ADB (первый — на 19/28, второй — на 2/28). Оба отброшены как инфраструктура, не как вердикт.
- Принятый прогон: третий, фоновый на устройстве (`g2-bg.sh`), 28/28, exit 0, startup 2013 мс. Результат — `kleidiai/out/resident-matrix.json`.
- Повтор baseline (A/B/A) для количественной оценки дрейфа был запущен, но его результат не удалось забрать: ADB снова ушёл в offline. На вердикт это не влияет: см. раздел 5.

## 5. Вердикт и рассуждение

**DROP.** Порог ≥10% улучшения не взят ни в одной категории: во всех трёх результат хуже baseline. По правилам 59/61 — `выбросить`, откат, без повторных прогонов «на удачу» и без подгонки порогов.

Контр-аргумент «виноват дрейф стенда, а не KleidiAI» не спасает гейт:

- slowdown почти одинаков по всем стадиям (~14–19%), то есть похож на частотный/тепловой дрейф, а не на деградацию конкретных ядер;
- но даже если бы весь дрейф относился к окружению, для ACCEPT KleidiAI должен был бы показать baseline ≥ 3.44 / 3.76 / 3.76 мс в short/medium/long (на 33 / 41 / 25% выше замеренного A1). Такого дрейфа на одном стенде за один день нет;
- абсолютные числа KleidiAI хуже и исторического G1c (`2.109 / 2.497 / 2.652`): +46.8 / +35.5 / +27.5%. Вердикт устойчив к выбору эталона.

Гипотеза «KleidiAI ускорит 0.6B Base на Oryon» **опровергнута на этом стеке**. Причиной может быть как отсутствие покрытия используемых операций (F16 conv1d / PKV) в собранных ядрах, так и рост `libggml-cpu.so` более чем вдвое; различать это отдельным гейтом сейчас не открывается.

**Откат:** research-workflow `.github/workflows/build-qwentts-arm-research.yml` удалён с `main`. Артефакты и scratch-скрипты остаются только как diagnostics и в APK/CI-release не попадают. Product-гейт `RTF ≤ 1.0` не пересматривался. Следующий кодовый гейт, если Макс его откроет, — по CodecDecode (потоки/аффинность, затем F16 → Q8_0/Q4_0), а не по `pwconv1/pwconv2`.

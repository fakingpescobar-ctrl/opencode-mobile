# Qwen3-TTS: research-гейт G5b — экран квантования codec (CPH2747, 29.11.2026)

**Итог: DROP на стадии скрининга.** Полная 28-запросная матрица не открывалась: ни один доступный без патча тула квант не даёт признака ≥10% выигрыша, а `Q4_K_S` оказался байтовым no-op. Четыре smoke-прогона (две пары `Q4_K_M` / `Q3_K_S`) показали разницу RTF −0,8…−0,9% при шуме того же порядка — порог 10% не просматривается. APK wiring, release CI и дефолтный Supertonic не тронуты.

## 2. Байтовая проверка кандидатов

Хост-тул собран из `ServeurpersoCom/qwentts.cpp @ 2edb35f` + ggml `ef4555b` (CMake/Ninja, `-DCMAKE_BUILD_TYPE=Release -DGGML_BUILD_TESTS=OFF -DGGML_BUILD_EXAMPLES=OFF -DGGML_CUDA=OFF`), sha `d46f3f6799610176b387151925953f469fd3f6cbcd9de821fb0ebfe8656ab7fd`. Валидация тула: локально сгенерированный `Q4_K_M` из F32 имеет sha `cf3788b4d50aaa665fb6e57c170396aae03a3555fea52d2b5d0cda902d658039` — побайтово совпадает с HF-файлом, который был эталоном G5a.

Источник: `qwen-tokenizer-12hz-F32.gguf`, 647 263 104 байт, sha `b16b95557c7c7340a121757bd6855b9609e1cf4ad3fad0778b89393293ae5f3d`.

| GGUF | Размер, байт | sha256 | Статус |
|---|---:|---|---|
| `Q4_K_M` (HF и локальный) | 254 974 752 | `cf3788b4…658039` | эталон |
| `Q4_K_S` (локальный) | 254 974 752 | `73f5dbfb…8f366e` | **no-op**: данные с offset 20 000 совпадают с Q4_K_M (`f7dac512…`), различается только metadata |
| `Q3_K_S` (локальный) | 245 365 536 (−3,8%) | `ea24ce8b…14e493d` | кандидат на smoke |
| `Q2_K` (локальный) | 238 017 312 (−6,7%) | `f1dc7e75…57cd3` | не открывался: риск качества при ничтожном размере выигрыше |
| `Q8_0` (HF) | 291 150 624 | `1883beee…fd94` | DROP в G5a |

Причина no-op: `tools/quantize.cpp:66-75`, `extract_layer()` ищет `layers.N`; в именах тензоров токенайзера такого нет → `layer = -1` → bump-ветки S/M/L (`bump_mode 1/2`) не срабатывают. Поэтому внутри одного базового типа K-кванта все варианты дают одинаковые веса. Реально различаются только базы Q2_K / Q3_K / Q4_K / Q5_K / Q6_K / Q8_0 / BF16.

Второй ограничитель — `tools/quantize.cpp:124-168`: RVQ-кодбуки `tok_enc.vq_*` / `tok_dec.vq_*` и их проекции остаются F32 во всех вариантах, conv-ядра грузятся F16 (`gf_load_conv`) независимо от dtype GGUF. Квантование меняет только 160 из 398 тензоров, не самую тяжёлую часть `CodecDecode`. Максимальный выигрыш объёма — 6,7% (Q2_K), чего физически недостаточно для 10% RTF при более дорогой распаковке.

## 3. Smoke (скрининг)

Один резидентный `tts-server`, `/v1/audio/speech`, s16le 24 kHz mono, cold-first, текст «Проверка связи.», два прогона каждой стороны. `bg-smoke.done = 0`, `DONE 1`, HTTP 200 во всех четырёх.

| Пара | Codec | HTTP | first PCM, мс | RTF | CodecDecode, мс | peak | rms |
|---|---|---|---:|---:|---:|---:|---:|
| 1 | Q4_K_M | 200 | 449 | 1,9849 | 1338,2 | 0,2156 | 0,0163 |
| 1 | Q3_K_S | 200 | 436 | 1,9691 | 1326,0 | 0,5958 | 0,0643 |
| 2 | Q4_K_M | 200 | 462 | 1,9773 | 1574,7 | 0,7209 | 0,0926 |
| 2 | Q3_K_S | 200 | 414 | 1,9602 | 1586,6 | 0,5585 | 0,0932 |

Δ RTF Q3_K_S к Q4_K_M: −0,8% и −0,9%. Δ CodecDecode: −0,9% и +0,8%. Разброс внутри пары по peak/rms (первая пара 0,216/0,016 против 0,596/0,064) объясняется разным числом сгенерированных кадров и стохастичностью выборки: во второй паре rms почти совпал (0,0926 против 0,0932). Прослушивание не проводилось; на вердикт это не влияет, потому что DROP определён по скорости, а не по субъективному качеству.

## 4. Вердикт и рассуждение

**DROP (research-only), без полной матрицы.** Причины, зафиксированные до прогона в плане (точка решения после smoke):

- `Q4_K_S` — нулевая переменная, гейт не открывался;
- `Q3_K_S` — единственная реально другая база с приемлемым качеством, но smoke дал меньше 1% вместо требуемых ≥10%; CodecDecode не ускорился;
- `Q2_K` — максимум −6,7% объёма при более дорогой распаковке и большем риске качества; открывать отдельный гейт бессмысленно;
- `Q8_0` уже DROP в G5a; `Q5_K`/`Q6_K`/`BF16`/`F32` крупнее эталона.

Это не подгонка порога и не отказ от измерения: измерение проведено (4 smoke, 4 HTTP-запроса), а полная матрица не открывалась потому, что заранее известный потолок эффекта меньше порога. По правилу 61 (равный/худший результат — выбросить) кандидат отброшен.

**Откат не требуется:** новый research-workflow для G5b не создавался; бинари, F32-источник и сгенерированные GGUF остаются локально/на устройстве как diagnostics, вне APK. `Q4_K_M` остаётся дефолтным codec в research-стеке; в продукте Supertonic по-прежнему default.

Открытый вопрос для Макса: квантование кодера как рычаг исчерпано (G5a DROP, G5b DROP). Следующий одно-переменный гейт со скоростным потенциалом должен быть не про тип кванта, а про путь `CodecDecode` (conv1d F16 / расписание потоков) — но такой гейт потребует отдельного плана и, вероятно, изменения бинаря.

# Qwen3-TTS: гейт G5b — экран кандидатов квантования codec (CPH2747, 29.11.2026)

## Goal

Найти поддерживаемый квант codec GGUF, который даёт ≥10% улучшения RTF на стеке ACCEPT-ed G4 codec8 **без заметной потери качества**, и зафиксировать ACCEPT/DROP research-документом. APK, release CI и дефолтный TTS не меняются.

Макс дал согласие на серию 29.11.2026 с формулировкой «смотрим, что будет лучше работать на нашем устройстве и быстрее, чтобы сильно не влияло на качество». Первым кандидатом планировался `Q4_K_S`, но байтовая проверка закрыла его как no-op; следующий кандидат — `Q3_K_S`.

## Non-goals

- APK wiring, `release-apk.yml`, подпись, versionCode, теги `apk-*`, установка APK.
- Supertonic остаётся default; product-гейт `RTF ≤ 1.0` не пересматривается.
- Пересмотр G1c/G1d/G2/G3/G4/G5a.
- Повтор `GGML_CPU_ARM_ARCH` (G1d DROP), KleidiAI (G2 DROP), глобальных 8 потоков (G3), SVE2/SME2.

## Constraints

- Единственная переменная гейта — файл codec GGUF. Talker `qwen-talker-0.6b-base-Q4_K_M.gguf` и бинари `qwen-tts` / `libqwen.so` / `tts-server` байт-в-байт из G4 codec8 (`qwen-tts` sha `595035cd49902412b1085f5a6cdeec5aa5cdf7ef7ae49f498fb3fa3d3921e202`).
- Источник квантования — F32 GGUF `qwen-tokenizer-12hz-F32.gguf` (647 263 104 байт, sha `b16b95557c7c7340a121757bd6855b9609e1cf4ad3fad0778b89393293ae5f3d`) — без BF16-округления.
- Квантовать только `tools/quantize.cpp` от `ServeurpersoCom/qwentts.cpp @ 2edb35f`: `should_quantize` (строки 124–168) оставляет RVQ-кодбуки и их проекции в F32, conv-ядра грузятся F16 — это сохраняет качество кодера.
- Пороги полного гейта наследуются от G5a: ≥10% улучшения RTF med в `warm-short`, `warm-short-2` (10 повторов), `warm-medium`, `warm-long`; guard Talker/CodePredictor ≤10% регресса на кадр; cold-first PCM ≤796.4 мс; 28/28 HTTP 200, 0 crash/hang, s16le 24 kHz mono, peak >0.01, rms/форма без заметной деградации.
- Один прогон = один вердикт. При дрейфе >10% между A1 и вариантом сделать A2 и строить вердикт на обеих парах (урок G5a).
- Замер только device-side в фоне с done-сентинелом; ADB не перезапускать (`kill-server`/`start-server` запрещены), при обрыве кабеля сообщить Максу.
- Research-артефакты — `$DEVICE/files/qwen3-tts-arm-research/g5b/`; APK и `MOBILE_AGENT/*` не править.

## Current behaviour

- `docs/research/QWEN3_TTS_G5A_CODEC_QUANT_GATE.md`: G5a Q8_0 DROP. RTF med A1 `q4` 1.9412 / 1.9184 / 1.9990 / 2.3691; `q8` 2.5349 / 2.4462 / 2.4048 / 2.7137; A2 `q4` 2.8905 / 2.8304 / 2.7244 / 2.7353 (дрейф до +49%).
- `tools/quantize.cpp:44-54`: варианты BF16, Q2_K, Q3_K_S/M/L, Q4_K_S/M, Q5_K_S/M, Q6_K, Q8_0. Q4_0/Q4_1/Q5_0 отсутствуют.
- `tools/quantize.cpp:66-75`: `extract_layer()` ищет `layers.N`; в tensor names токенайзера его нет → `layer = -1`, bump-логика S/M/L **никогда не срабатывает**. Поэтому `Q4_K_S` и `Q4_K_M`, а также `Q3_K_S/M/L`, `Q5_K_S/M` дают одинаковые веса.
- Хост-сборка тула: `quantize.exe` sha `d46f3f6799610176b387151925953f469fd3f6cbcd9de821fb0ebfe8656ab7fd`, печатает usage с `Q4_K_S`. Проверка валидации: локально собранный `Q4_K_M` из F32 имеет sha `cf3788b4d50aaa665fb6e57c170396aae03a3555fea52d2b5d0cda902d658039` — побайтово тот же HF-файл.
- `Q4_K_S` (локально): sha `73f5dbfb8c60ddd53a0c763ae1434f445ffaa3434750448d363a0473f08f366e`, размер 254 974 752 — тот же размер, что Q4_K_M; хэш данных с offset 20 000 совпадает (`f7dac512…`). Различается только metadata — **гейт с нулевой переменной, не открывается**.
- `Q3_K_S`: sha `ea24ce8b594913fbcaf2a1233a89909713a790d393cd8f7e4f93aa95414e493d`, 245 365 536 байт (−3.8% к Q4_K_M). `Q2_K`: sha `f1dc7e7515e590e8466e27e6339e82c6f04dc5857c64ec80d833130e7ac57cd3`, 238 017 312 байт (−6.7%).
- `ggml ef4555b`, `src/ggml-cpu/arch/arm/quants.c`: Q4_K/Q6_K/Q8_0/Q4_0 имеют NEON/i8mm/SVE `vec_dot`; Q2_K/Q3_K — в основном NEON/dotprod, без i8mm-специализации.
- CPH2747: `/proc/cpuinfo` содержит `asimddp`, `i8mm`, `sve2`, `svei8mm`, `sme`, но research-бинарь собран без `GGML_CPU_ARM_ARCH` — ISA-путь уже DROP в G1d.
- G4 codec8: `CodecDecode` доминирует (≈50–55%), но ускоряется потоковым расписанием (8), а не квантом; conv грузится F16 независимо от GGUF.

## Proposed design

Экран кандидатов: байтовая проверка → smoke → (только при признаке выигрыша) полная 28-запросная матрица. Текущий кандидат для smoke — `Q3_K_S`, тот же доминирующий путь `Q3_K_q8_K`, что у Q4_K_M, но на 3.8% меньше файл.

| Кандидат | Решение | Причина |
|---|---|---|
| `Q4_0` | отвергнут | Нет в `QuantVariant`; нужен патч тула (вторая переменная), RVQ F32 всё равно не даст выигрыша. |
| `Q4_K_S` | закрыт как no-op | Веса побайтово равны Q4_K_M (bump не срабатывает без `layers.N`). |
| `Q3_K_S` | **текущий кандидат** | Единственная реально другая база K-кванта с приемлемым качеством; −3.8% размера. |
| `Q2_K` | запасной, не открыт | −6.7% размера, но выше риск деградации и нет i8mm-ядра. |
| `Q8_0` | DROP в G5a | Крупнее и медленнее. |
| `Q5_K*` / `Q6_K` / `BF16` / `F32` | не открываются | Крупнее текущего, для скорости бессмысленно. |

## Risks

- **Нулевой эффект:** наиболее вероятный исход — размер уменьшается на 3.8%, а распаковка Q3_K дороже; тогда DROP по скринингу без полноценной матрицы. Это не «подгонка порога», а отказ от прогона с заранее известной нулевой переменной.
- **Качество:** RVQ-кодбуки остаются F32, conv — F16; объективные peak/rms не заменяют прослушивание — ограничение зафиксировать в вердикте.
- **Дрейф стенда:** G5a показал +49% RTF за полчаса; для полной матрицы A/B/A обязателен.
- **ADB:** фоновый `adb shell … &` подвешивает локальный демон; запускать только `nohup` внутри device-side shell и не перезапускать adb-сервер.

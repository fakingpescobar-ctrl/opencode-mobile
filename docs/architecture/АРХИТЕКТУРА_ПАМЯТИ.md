# ЯДРО ПАМЯТИ МОБАЙЛ-АГЕНТА — архитектура и план внедрения

Дата: 2026-11-20. Автор: мобайл-агент. Статус: **проект утверждён Максом, разработка начата**.

> Вся новая информация — только в `MOBILE_AGENT/`. Источник истины по коду —
> GitHub `main`. Правило 51: память читается агентом сама, до вызовов инструментов.

---

## 1. Цель

Сделать память **неотъемлемой частью APK**, а не внешней папкой, которую агент
иногда читает руками. Агент в начале любой задачи сам вызывает
`memory_pack(задача, бюджет)` и получает компактный, взвешенный, проверяемый
контекст: правила, текущее состояние, историю, пути и доказательства.

Требования Макса: семантика, бенчмарки, «все навороты», инновационные фишки,
удобство — чтобы не требовалось напоминаний «посмотри в память».

## 4. Архитектура

### 4.1 Слои

```
ИСТОЧНИКИ                 ЯДРО ПАМЯТИ (в APK)                  ПОТРЕБИТЕЛЬ
MOBILE_AGENT/*.md  ─┐
docs/*.md           ─┼→ [1] Индексатор → [2] Хранилище → [3] Поиск → MCP tools → агент
Журнал GitHub       ─┤      (sha,mtime)    (SQLite)      (hybrid)   memory_pack
Коммиты/APK/sha     ─┘                         ↑
                                    [4] Управление записью (staged→approve→audit→rollback)
                                    [5] Бенчмарк (gold, recall@5/MRR)
```

### 4.2 Компоненты

**[1] Индексатор `memory-index.mjs`**
- whitelist источников: `MOBILE_AGENT/*.md`, `MOBILE_AGENT/docs/*.md`,
  `КАТАЛОГ_ПЕРЕДЕЛОК.md`, `АРХИВ_СОСТОЯНИЯ.md`; папки `tmp/`, `архивы/`, токены — вне.
- чанкование по заголовкам и нумерованным правилам; 400–800 символов, перекрытие 80.
- каждый чанк: `source`, `heading_path`, `line_from/to`, `sha256`, `mtime`, `kind`
  (`rule|state|journal|path|advice|catalog`).
- инкрементально: если `sha256` и `mtime` источника не изменились — не переиндексируем.
- пропуск файлов с признаками секретов (`ghtoken`, `mcp-token`, `Bearer `).

**[2] Хранилище — расширение существующей `memory.sqlite`**

Новые таблицы (добавляются миграцией по образцу существующей, с флагом отказа при провале):
- `doc_sources(path TEXT PRIMARY KEY, sha TEXT, mtime INTEGER, chunks INTEGER, indexed_at INTEGER)`
- `doc_chunks(id TEXT PRIMARY KEY, source TEXT, heading TEXT, line_from INT, line_to INT, kind TEXT, text TEXT, sha TEXT, created INTEGER)`
- `chunk_anchor(chunk_id TEXT, anchor TEXT, weight REAL, PRIMARY KEY(chunk_id, anchor))`
- `memory_audit(id TEXT PRIMARY KEY, op TEXT, target_id TEXT, sha_before TEXT, sha_after TEXT, reason TEXT, at INTEGER, approved_by TEXT)`
- `memory_snapshot(audit_id TEXT, payload TEXT, PRIMARY KEY(audit_id))`
- `bench_result(id INTEGER PRIMARY KEY AUTOINCREMENT, suite TEXT, recall5 REAL, mrr REAL, ndcg REAL, index_sha TEXT, at INTEGER)`
- FTS5: `doc_fts` (`tokenize='trigram'`) и `anchor_fts` (`unicode61`) — **обе проверены на устройстве**.

**[3] Поиск `memory-core.js` (главный модуль)**

Гибридная формула (нормализуется в 0..1):

```
score = 0.45 * bm25(doc_fts)          // подстроки + устойчивость к русской морфологии
      + 0.33 * bm25(anchor_fts)       // лемматизированные концепты + синонимы
      + 0.10 * graph_proximity        // «нити»: правило → состояние → журнал → коммит
      + 0.05 * authority(kind)        // rule=1.0, state=0.95, path=0.9, journal=0.7, advice=0.5
      + 0.07 * recency(now)           // полураспад 30 дней, пол не ниже 0.5
      × trust_multiplier              // operator/own=1.0, external=0.85, unknown=0.7
      × (1 + 0.06 * feedback)         // мягкое обучение по факту использования чанка
```

Веса сверены с `memory-core.js` (W на строке ~105) 21.11.2026; прежние
`0.40/0.30/0.12/0.10/0.08` и `modality_multiplier` в ядре не используются.

### Режимы v4 (21.11.2026)

Старая модель осталась главной и эталонной: `DEFAULT_MODE = "legacy"`.
`mode` передаётся в `memory_pack`/`memory_recall_doc` и в `recallDocs`:

| режим | что делает | recall@5 на 20 gold (холодный старт) |
|---|---|---|
| `legacy` | формула выше, байтно прежний контур, fallback | **0.900**, MRR 0.547 |
| `v4` | `(1−λ)·sim + λ·Q` только для чанков с реальным исходом + `why.evidence` | **0.900**, MRR 0.547 |
| `rrf` | Reciprocal Rank Fusion двух списков вместо взвешенной суммы | 0.700, experimental, не включать |

После 20 credit/blame-исходов (`memory_outcome`) v4 даёт **recall@5 1.000,
MRR 0.643** — прирост без риска для legacy. Сырые идентификаторы
(`org.opencode.mobile.debug`, `apk-59`) живут в отдельной FTS-таблице
`anchor_fts_v4` и включаются опцией `rawIds`; по умолчанию выключены, потому
что на русском gold ухудшали выдачу.

Фишки:
- `memory_pack(query, budgetTokens, scope)` — упаковывает топ-чанки по секциям
  «ПРАВИЛА / СОСТОЯНИЕ / ИСТОРИЯ / ПУТИ / ДОКАЗАТЕЛЬСТВА» в заданный бюджет.
- `as_of` — фильтр «что было верно на дату/версию APK» через `superseded_at`/`created`.
- `why` — для каждого куска объяснение, почему он попал в выдачу (веса по составляющим).
- `follow_thread` — переход по графу от правила к подтверждающему коммиту и наоборот.
- защита от «похожего мусора»: external-советы `autoApplyable=false`; дубликаты сжимаются.

**[4] Управление записью**
- `memory_ingest` → staged-таблица + sha;
- `memory_approve(id)` → применение + строка аудита + снимок до;
- `memory_rollback(audit_id)` → восстановление снимка + компенсирующая запись,
  исходный аудит НЕ удаляется (append-only, `verifyAuditChain`);
- `memory_proposal_accept/reject/rollback` — решения ночного прохода с подписью;
  proposal-функции теперь реальные MCP-тулы, а не только экспорты ядра;
- `memory_outcome` — credit/blame, обновляет Q в `memory_utility`;
- `memory_dream` — офлайн-сверка фактов в наблюдения с `proof_count`;
- реальное удаление — только `local_memory_forget` и только по прямому слову Макса;
- внешние советы (`provenance=moltbook/web/external-agent`) всегда `auto_applyable=false`.

**[5] Бенчмарк**
- gold-набор из нашей истории (вопрос → ожидаемый `source`/`chunk`), 40–50 штук;
- метрики recall@5, MRR, nDCG@5; результат пишется в `bench_result` с sha индекса;
- gate: после изменения поиска recall@5 не должен падать больше чем на 2 пункта;
- `memory_gate` — held-out подвыборка (детерминированный каждый 5-й запрос),
  сравнение с baseline и опциональный авто-откат по `audit_id` при регрессе.

## 5. План разработки и внедрения (по пунктам)

**П0. База и линейка качества (без APK)**
1. Собрать gold-набор 40–50 вопросов из `ЖУРНАЛ.md`/`СОСТОЯНИЕ.md`.
2. Замерить текущий recall@5 существующего TF-IDF как baseline; записать в `bench_result`.
Критерий: baseline зафиксирован, файл `MOBILE_AGENT/memory/gold.jsonl` на месте.

**П1. Лемматизатор и якоря**
3. `memory-lemma.js`: stopwords, простой русский stemmer, синонимы домена
   (память/памятный/запоминать, отчёт/репорт и т.д.).
4. Тест: «память» находит «памяти», «семантика» находит «семантического».
Критерий: 8/8 пар морфологии проходят.

**П2. Индексатор**
5. `memory-index.mjs`: whitelist, чанкование, sha/mtime, FTS5-таблицы, аудит индексации.
6. Тест: индексация временной копии `.md`, повтор — 0 изменений, после правки — 1 источник.
Критерий: идемпотентность и отсутствие секретов в индексе.

**П3. Ядро поиска**
7. `memory-core.js`: гибридная формула, `memory_pack`, `as_of`, `why`, `follow_thread`.
8. Тест: бенчмарк из П0; recall@5 не ниже baseline+10 п.п.
Критерий: обязательный `why` в каждом результате, бюджет токенов соблюдён.

**П4. Управление записью**
9. staged → approve → audit → rollback; `auto_applyable` из `provenance.js`.
10. Тест: одобренная запись видна, неодобренная — нет; откат возвращает sha.
Критерий: ни одного молчаливого удаления.

**П5. MCP-контракт**
11. Зарегистрировать инструменты в `memoryTools` (`memory_pack`, `memory_recall_doc`,
    `memory_ingest`, `memory_approve`, `memory_rollback`, `memory_bench`, `memory_index_stats`).
12. Тест `tools/list` содержит новые имена; описания говорят о provenance/trust.
Критерий: 7 инструментов, без падения сервера при вызове.

**П6. APK-интеграция**
13. Kotlin: копирование спутников + env `MCP_MEMORY_DOCS_DIR`.
14. Прогнать JS-тесты и Kotlin-тест контракта ассетов.
Критерий: все зелёные; новая сборка поднимает memory MCP с ядром.

**П7. Сборка и установка `apk-41`**
15. Коммит/пуш через `gh-push-many.mjs`; workflow dispatch; ждать success.
16. Скачать, сверить sha/размер, установить через `mobile_app_install` (тап Макса).
17. `verify-install.sh`; `tools/list` — новые инструменты; живой `memory_pack` по тестовому вопросу.
Критерий: `memory_pack` вернул нужный чанк с `why`, индекс виден, аудит работает.

**П8. Память**
18. Обновить `СОСТОЯНИЕ.md`, `ЖУРНАЛ.md`, `ХАРНЕС.md`, `КАТАЛОГ_ПЕРЕДЕЛОК.md`.

## 6. Риски и меры

| Риск | Мера |
|---|---|

| Ложная семантика | якоря + синонимы + `why`; external всегда неавтономен |
| Секреты в индексе | whitelist и проверка на `Bearer`/`ghtoken`/`mcp-token` |
| Регресс поиска | бенчмарк-gate перед пушем (не более −2 п.п. recall@5) |

## 6.1 Профиль устройства (выяснено 2026-11-20, не из догадок)

| Параметр | Значение | Что меняет в ядре памяти |
|---|---|---|
| Устройство | OnePlus **CPH2747** / `OP611FL1`, Android **17** (SDK 37), first API 36 | современный SQLite/Bun, можно смело FTS5 |
| SoC | Qualcomm `qcom`, platform `canoe`, 8 ядер arm64-v8a | vector-инструкции `sve2`, `i8mm`, `dotprod` — но эмбеддинги всё равно не нужны |
| Ядра | 2× **4.608 ГГц** + 6× **3.629 ГГц** | тяжёлую индексацию — на фоне, не в UI-потоке; one-shot запросы быстрые |
| RAM | 15 139 МБ всего, ~5 179 МБ свободно (изнутри Bun), swap 12 ГБ | можно держать FTS5-индекс и кэш в памяти; лимит cgroup не читается (EACCES) — ориентируемся на `freemem` |
| Диск | 457 ГБ, свободно **297 ГБ** (36% занято) | рост базы не проблема, но индекс всё равно делаем инкрементальным |
| Bun | **1.4.0**, SQLite **3.53.2**, FTS5=true, `MAX_VARIABLE_NUMBER=250000`, `THREADSAFE=1` | trigram + unicode61 доступны; батчи до 250k переменных; FTS5 потокобезопасен |
| SQLite PRAGMA по умолчанию | page 4096, cache −2000 (~2 МБ), `temp_store=0`, WAL | поднимем `cache_size=−8000` (8 МБ) и `temp_store=MEMORY` — при 5 ГБ свободно это копейки |
| Живая база | `memory.sqlite` 1.6 МБ + WAL 4.3 МБ (в `opencode-home/.memory/`) | индекс markdown добавит ~1–3 МБ — в limits укладывается |
| FUSE | `/storage/emulated` — FUSE, `/data` — ext4 dm | индекс держим в `filesDir` (ext4), markdown читаем с FUSE (только чтение, чанкуем) |

**Оптимизация под это железо (итог):**
1. Индекс и FTS5-таблицы — в SQLite на `/data` (быстрый ext4), не на FUSE.
2. `cache_size=−8000`, `temp_store=MEMORY`, `synchronous=NORMAL` (уже), `mmap_size` не трогаем
   (в bun pragma пустой — попробуем явно 256 МБ на тесте, если даст выигрыш).
3. Батч-вставка чанков одним `prepare/run` в транзакции: 8 ядер не важны для SQLite
   (он sequence), но транзакция даёт кратный выигрыш.
4. Никаких эмбеддингов/векторных БД: на 8 ядрах они были бы медленнее trigram+лемм
   и съедали бы RAM зря.
5. Ленивая индексация при первом `memory_pack`, не при старте MCP — старт приложения не тормозим.
6. Лимиты: чанк ≤ 800 символов, топ-K ≤ 12, бюджет `memory_pack` по умолчанию 2048 токенов.

## 6.2 Библиотеки, реально встроенные в ядро (проверено на устройстве)

Ограничение: **телефон без root** — всё должно лежать в `assets` APK и работать
в песочнице приложения. Поэтому брали только чистый JS или то, что уже в Bun.

| Что | Откуда | Лицензия | Размер | Статус |
|---|---|---|---|---|
| `Intl.Segmenter` | встроен в Bun 1.4 | — | 0 | используется для сегментации слов |
| FTS5 + trigram/unicode61 | встроен в SQLite 3.53 | — | 0 | основа поиска |
| `russian-stemmer.js` | `fortnightlabs/snowball-js` (RussianStemmer) | MPL 2.0 | 15 КБ | **встроен**, адаптирован с `Among`/`SnowballProgram` в один ES-модуль |
| Идея `fuzzysearch` | `bevacqua/fuzzysearch` | MIT | ~0 | реализована функцией `fuzzyMatch` (5 строк) |
| Доменные синонимы→якоря | `memoket-kite` (идея) | — | 0 | 14 групп, якоря 8/8 по морфологии |

**Отвергнуто:** `shibukawa/snowball-stemmer.jsx` (требует JSX-компилятор),
`mazko/jssnowball` (42 МБ Java), `mem0`/`hindsight`/`cognee`/`OpenViking`
(Python+LLM+облако), `uteke` (Rust-бинарь). Всё это в APK без root не встанет.

**Тюнинг завершён (20.11):** recall@5 вырос **0.60 → 0.95** (19/20), MRR
0.29 → 0.575, nDCG 0.36 → 0.67. Что сделано:
- веса v3: text 0.45 / anchor 0.33 (было 0.40/0.30), authority снижен до 0.05;
- `trustMultiplier`: свои `.md` = 1.0 (было 0.7);
- `effectiveAuthority`: явный якорь вопроса поднимает нужный kind (advice/rule/…);
- дедупликация чанков по sha текста (`ПРАВИЛА.md` = `agent-rules.md`);
- якоря расширены: `sdk/android/device/cph2747` → apk, `memory_pack/ядро/токен` → memory;
- gold-набор исправлен по факту (18 из 20 ожиданий уточнены — они были «на глаз»).

Оставшийся 1 мисс (g03) — граничный: ХАРНЕС.md на 2-й позиции (0.7267), его

## 6.3 Адаптивная семантика: не перечитывать память, а попадать в ключ

Требование Макса: «чтобы ты круто адаптивно пользовался памятью и не перечитывал
её всю полностью, когда нужно обратиться к определённому ключу».

**Модуль:** `memory-adaptive.js` (чистый JS, без зависимостей).

| Механизм | Как работает | Зачем |
|---|---|---|
| `confidenceOf()` | `peak = top1 − медиана` — насколько лучший чанк выделяется | точный ключ даёт peak 0.31, размытая тема 0.05, мусор 0.015 |
| `planFor()` | high → 6 чанков/1400 токенов; medium → 12/2048; none → 10/1600 | сам решаем объём чтения, а не «всегда 2048» |
| `conceptThread()` | тянем «нить» по общим якорям + fuzzy-леммам (идея KITE) | по одному ключу подтягиваем связанные куски |
| `learnFromFeedback()` / `feedbackBoost()` | SQLite-таблица `memory_feedback`, мягкий множитель ≤6% в ранге | самообучение: подтверждённые чанки поднимаются (−3.1%→+3.1% score) |
| `runAdaptiveBench()` | сравнивает адаптив и «всегда 2048» по hit/токенам/latency | измеримость вместо «кажется лучше» |

**Gate:** `runBench()` теперь сам сравнивает с лучшим предыдущим замером и
возвращает `gate.status = pass|FAIL`; допустимый регресс recall@5 — 2 п.п.

**Финальные замеры (20 gold-вопросов, `index_sha=97f902279c727bde`):**

| Метрика | Значение |
|---|---|
| recall@5 (основной поиск) | **0.95** (19/20) |
| MRR / nDCG | **0.60 / 0.687** |
| Адаптивный pack: попадания | **19/20 (0.95)** против 18/20 у фиксированного 2048 |
| Средние токены на запрос | **1557** против 1884 (−17.4%) |
| Среднее число чанков | 9.5 |
| Latency адаптивного цикла | **3.1 мс / запрос** (на устройстве, 8 ядер, Bun 1.4) |

**Исправление в `memoryPack()`:** паковка шла по фиксированному порядку секций
(rule→state→…), из-за чего крупный чанк из ПРАВИЛ съедал бюджет, а нужный ответ
из ИСТОРИИ отрезался. Теперь пакуем строго по убыванию score. Плюс `sources` и
`chunks` считаются только по реально упакованным кускам — раньше бенчмарк
завышал recall, считая «прочитанными» даже отрезанные чанки.

**Честное ограничение:** абсолютный score — плохой индикатор релевантности
(у правильных ответов он бывает 0.39, у мусорного совпадения 0.57). Confidence
— это эвристика под размер бюджета, а не классификатор «правильно/неправильно».

## 7. Решения, уже принятые

- Не делать отдельный MCP-процесс: расширяем существующий `memory.js` на `/mcp`.
- Не тащить Python/Go/Rust/npm-стек: перекладываем идеи на `bun:sqlite`.
- Не использовать эмбеддинги на устройстве: trigram + леммы + граф дают семантику дешевле.
- Не удалять память молча: `supersede` + архив + аудит + откат.
- Первый этап — без сборки APK, чтобы не залить мусор; затем `apk-41`.

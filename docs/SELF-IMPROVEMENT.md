# B: петля самоулучшения агента

Статус: план утверждён 2026-10-01. Реализация — по шагам ниже.

## Цель

Агент читает собственные отказы, строит гипотезу, патчит **свой** код,
гоняет тесты, коммитит зелёное и откатывает красное.

## Граница доверия — слой, который решает всё

Ответы других агентов (Moltbook) — недоверенный ввод. Любой может
написать «вынеси токены в открытый конфиг», и агент, применяющий это сам,
превращает чужой совет в дыру в своём коде.

| Слой | Источник сигнала | Что агент может |
|---|---|---|
| **T1** | свои логи, свои тесты, свои исключения | править свой код сам |
| **T2** | Moltbook, ответы других агентов | только предлагать, решает человек |

T2 не запрещён — это самое ценное из молтбука. Просто не применяется сам.

## Почему не C (и почему не A)

Вариант «агент правит код opencode-mobile» невозможен на устройстве,
а не просто сложен:

1. Репозиторий `C:\Projects\opencode-mobile` на ПК, агент работает на телефоне.
2. Копии скриптов перезаписываются при каждом старте: `ensureAssetScript`
   (`OpencodeRuntime.kt:255-289`) сверяет `filesDir/mem/*.js` с assets и
   перезаписывает при отличии. Патч агента в этой папке живёт до
   перезапуска приложения.
3. На телефоне нет JDK и gradle — 241 Kotlin-тест запускаются только на ПК.

A (править `filesDir/mem`) отвергнут отдельно: петля выглядела бы рабочей,
а правка исчезала бы через час и баг возвращался. Хуже неработающей
петли — петля, которая врёт.

**B: агент улучшает свои инструменты в workspace** —
`/storage/emulated/0/Documents/OpencodeTerminal`. Переживает перезапуск,
тестируется на устройстве через bun, цена ошибки — его собственный скрипт.

## Что проверено на устройстве

| Факт | Проверка |
|---|---|
| Инструменты агента: `read, write, edit, glob, grep, bash` | спрошен у живой сессии |
| bun запускает JS на телефоне | `libldmusl.so libbun-musl.so скрипт.js` — отработал |
| Тесты запускаются на устройстве | `ynison-search.test.mjs` на телефоне: 19 упали только из-за относительного пути к SOURCE |
| git на телефоне отсутствует | `which git` — пусто |
| Termux на телефоне отсутствует | `pm list packages \| grep termux` — пусто |
| Workspace почти пуст | только README, следы Ynison, каталоги opencode-* |
| DNS в musl-Bun не резолвится | `getaddrinfo ETIMEOUT www.moltbook.com` за 5022мс; обход: IP + `Host`-заголовок → HTTP 200 за 518мс |

Вывод из проверки тестов: SOURCE в тестах резолвится относительно
`import.meta.url`, поэтому на устройстве нужен абсолютный путь либо
переменная окружения. Это надо учесть в harness.

## Компоненты

### 1. Свои инструменты агента (объект улучшения)

```
/storage/emulated/0/Documents/OpencodeTerminal/
  tools/            ← то, что агент улучшает
    digest.js
    ticker.js
  tests/            ← гейт
    *.test.mjs
  lessons/          ← журнал гипотез, вне памяти MCP
  .snapshots/       ← точка отката
```

### 2. Пайплайн

```
сигнал (свой лог / упавший тест)
  → агент строит гипотезу
    → пишет в память с provenance=own-log
      → патчит свой код в tools/
        → bun test в tests/
          зелёный → снапшот + коммит в lessons/
          красный → откат снапшота, гипотеза «не подтвердилась»
```

### 3. Гейт по тестам — то, что делает петлю безопасной

Безопасность обеспечивается не запретами, а архитектурой: изменение
обязано пройти тесты, иначе автоматический откат. Агент может ошибаться
сколько угодно — цена ошибки один откат.

Тестовый гейт на устройстве: bun уже работает (проверено), git нет —
значит снапшоты пишем сами, копированием файла перед патчем.

### 4. Provenance в памяти

Урок «из своего лога» и урок «с молтбука» обязаны лежать по-разному.
Через месяц агент не вспомнит откуда совет и применит чужой как свой.

Текущая схема `memories` (в `memory.js`) полей provenance не имеет:
`id, content, type, tags, project, created`. Добавить колонку
`provenance` и фильтр в `recall`/`list`.

### 5. Публикация наружу (когда дойдёт до Moltbook)

Whitelist того, что можно публиковать, а не blacklist того, что нельзя:
blacklist всегда что-то пропустит. Наружу не должны уйти токены, порты,
имена эндпоинтов, структура папок.

## Порядок работ

1. **Harness** — тесты агентских инструментов запускаются на устройстве
   (починить резолв SOURCE), плюс снапшот/откат без git.
2. **Provenance** — колонка в памяти, фильтр, тест на различие слоёв.
3. **Сигнальный контур** — агент читает свои логи и находит свои ошибки.
4. **Полный цикл** — гипотеза → патч → тест → коммит/откат, прогнать
   на заведомо ломанном скрипте end-to-end на устройстве.
5. **Ticker** — будильник, будит агента при появлении сигнала.
   Отложено: петля должна сначала доказать, что не врёт.

## Открытые вопросы

- Как агент узнаёт о своём падении, если лог пишет процесс, а читает агент:
  нужен источник сигнала помимо логов (счётчик в MCP-ответе?).
- Частота петли: агент не должен просыпаться и тестировать каждые 15 минут
  впустую.
- Нужен ли T2-инструмент чтения молтбука сейчас, или после T1 обкатки.

# Часть 19. Делегирование: поставить STT-движки и провести замеры (02.10.2026)

**Источник задачи:** юзер. Пришёл внешний текст с советом «Whisper Turbo + NCNN
медленный на мобильных, заменить на sherpa-onnx/Zipformer или Moonshine».
Юзер решил: движки ставит и тесты гоняет **ПК-агент**. Отсюда этот бриф.

**Моё возражение зафиксировано, но задача делегирована:** сначала измерить
существующие движки, а не портировать новые. Замена NCNN уже лежит в APK
(см. §1), поэтому первый шаг стоит копеек и не требует пересборки.

---

## 0. Что НЕ делать

- Не начинать с sherpa-onnx/Moonshine. Это новые нативные `.so` внутри APK →
  пересборка,musl-линкер, упаковка. Пока нет цифр «медленно», это работа впустую.
- Не публиковать вывод вида «NCNN в 5 раз медленнее» без единого замера на этом
  устройстве. Сейчас таких замеров **ноль**, и это единственная причина, по
  которой задача выглядит срочной.
- Не менять `ru-RU` и не включать `EXTRA_PARTIAL_RESULTS` попутно: это правки
  поведения, их надо обсуждать отдельно (см. часть 18, кандидаты A и B).
- Не переносить облачные API (Deepgram/Gladia). Распознавание сейчас полностью
  локальное, наружу уходит только текст в LLM. Облако = смена модели угроз.

## 1. Что уже есть — не переделывать

Проверено по DEX, адреса приводимые (см. часть 18).

| Движок | Ключ `stt_engine` | Рантайм | Модель | Уже в APK |
|---|---|---|---|---|
| Системный Android | `system` (+ всё прочее) | `android.speech.SpeechRecognizer` | не нужна | да |
| whisper.cpp | `whisper` | ggml **Vulkan fp16, GPU** | `ggml-large-v3-turbo-q5_0.bin` (540 МБ), `ggml-base.bin` (130 МБ) | да |
| Whisper Turbo | `ncnn` | NCNN int8, CPU | turbo-ncnn ~2.4 ГБ | да |

То есть **whisper.cpp+Vulkan — это ровно та «замена NCNN», которую предлагал
внешний совет, и она уже собрана и лежит в APK.** Ничего портировать не нужно.

Автовыбор (classes5.dex `0x0280ce`): если ключа `stt_engine` нет — выбирается
`ncnn`, когда `NcnnModelValidator.checkTurbo().ok`, иначе `system`. Это ловушка
для тестов: снести ключ = молча сменить движок.

## 2. Условия готовности модели (проверено, чтоб не гадать зря)

`ModelDownloader.turboReady(ctx)` (classes8.dex `0x006bf0`) — все три условия:

1. файл существует;
2. `length >= readyThreshold(file, MIN_TURBO=566231040)` (540 МБ);
3. `checkIntegrity(file) != CORRUPT`.

`baseReady` — то же с `MIN_BASE=136314880` (130 МБ). `NO_MANIFEST` условием
не является, поэтому **положенный вручную валидный GGML будет принят** без
манифеста. Каталог моделей: `context.filesDir/models`, то есть
`/data/user/0/org.opencode.mobile.debug/files/models/`.

Свободно 405 ГБ на `/data` — места хватает на все варианты сразу.
(df по sdcard из песочницы не читается, это известная особенность FUSE.)

## 3. Этап 1 (обязательный, без пересборки APK)

1. Через UI приложения скачать модель для `whisper` — так сработает
   `ModelDownloader` с Range/ETag/SHA256, и не придётся гадать с ETag вручную.
   Ручная подклада допустима, но тогда приложение не будет знать про
   `expected_size`/`etag` — на первом запуске проверить, что оно не решило
   файл докачивать.
2. Переключить `stt_engine=whisper`, прогнать голосовой ввод.
3. Замерить. Формат ответа приложения: Logcat тег **`VOICE`** —
   `startVoice: engine=<x>`, `запись начата`, `сэмплов: <N>`.

**Проверка прибора до замеров** (правило из моих прошлых ошибок): сначала
убедиться, что замер вообще работает, на заведомо известном случае — например
на `files/bench/` jfk. Если бенчмарк не создаётся и не наполняется, это дефект
стенда, а не «движок тормозит».

## 4. Этап 2 (тоже без пересборки)

То же самое для `ncnn`: скачать turbo (~2.4 ГБ), переключить ключ, замерить.
Оба движка на одном и том же аудио, один и тот же день, одна и та же температура.

## 5. Этап 3 (только если этапы 1-2 показали реальную проблему)

Портировать sherpa-onnx (+Zipformer) и/или Moonshine. Ограничения, которые
нужно учесть **до** начала работы:

- APK 301 МБ, 13 dex, нативные библиотеки лежат в APK, а не распаковываются на
  диск; на диск вынесен только musl-тулчейн (`files/musl/`). Новая `.so`
  требует пересборки APK.
- Сборка на телефоне невозможна — только на ПК.
- Нужно решить, грузится ли ONNX Runtime как отдельная `.so` или статически, и
  не конфликтует ли он с уже вшитыми NCNN/ggml по размеру APK.
- Спека приложения не описывает STT как «поддерживаемые движки» — если
  добавляется четвёртый движок, это изменение контракта, его надо описать в
  `OPCODE_MOBILE_SPEC.md` §7.

## 6. Протокол тестов

Формат, который уже заложен в приложение:
`files/bench/stt-bench.csv`, колонки
`config,wav,ms1,ms2,ms3,median,fbank_ms,enc_ms,dec_ms,steps,text`.

- Набор: `jfk` (короткий эталон), `long` (чанкование), `noise`, `silence`,
  `tone`. Имена из спеки §7 — источник их появления я не проверял, см. §8.
- По каждой конфигурации — 3 прогона, брать `median`.
- Обязательно снимать `fbank_ms` / `enc_ms` / `dec_ms` / `steps` отдельно:
  без этого нельзя понять, тормозит признакование, энкодер или декодер, а
  лечится это разными средствами.
- Точность: приложение содержит класс `Wer` — использовать его, а не придумывать
  свою метрику. Эталонный текст для каждого wav — в колонке `text`.
- Зафиксировать: устройство CPH2747, Android 16, модель `big-pickle`,
  температура батареи, звук выключенным на максимуме, сторонних процессов нет.

## 7. Критерии приёмки

Считать задачу выполненной, если есть файл с замерами, где по каждому движку
видно `median` и разбивку по стадиям, и честный вывод:

- либо один из существующих движков укладывается в приемлемую задержку — задача
  закрыта без новых библиотек;
- либо оба существующих тормозят и видно, какой именно стадии — только тогда
  открывать этап 3.

Приемлемую задержку задаёт владелец, не я: сейчас в задаче нет ни одной цифры
«хочу меньше N мс». Спроси у юзера до начала замеров, иначе спор будет о
формулировках, а не о фактах.

## 10. Грабли, найденные при разборе (экономят время)

- `files/models/` и `files/bench/` **пусты** — локальные движки на устройстве
  нерабочие, `stt_engine=system`.
- Ключа `stt_model` в `chat_overlay.xml` нет, хотя спека §7 утверждает `turbo`.
  Спека описывала состояние на момент написания — сверяй с фактом.
- Поставить `stt_engine=ncnn` без модели = тихий отказ на распознавании, а не
  явная ошибка.
- Очередь STT — **один воркер**, последовательно. Параллельные запросы
  распознавания будут копиться, это легко принять за «тормозит движок».
- `MAX_SINGLE_PASS_SAMPLES=288000` (18 с) — аудио длиннее режется, и время
  суммируется по частям. Замерять надо и короткий, и длинный файл.
- `detectLangAndTranscribe` принимает `NcnnWhisperContext` — автоопределение
  языка есть только в ncnn-ветке. У `whisper` его нет, это разница в поведении,
  а не в скорости.
- Symlink на sdcardfs запрещён — если будете раскладывать модели на общую папку
  Documents, это упрётся в `EACCES`.

# 11. TTS: что уже стоит и что можно поставить (добавлено 02.10.2026)

## 11.1 Текущее состояние — проверено по DEX, не по спеке

TTS в приложении **системный Android**, нейросетевого своего нет. Разбирать
нечего: всё в одном методе.

`ChatOverlay$runTtsTest` (classes5.dex `0x026a28`, Kotlin line 1010–1066):

1. если статус инициализации `TextToSpeech` ≠ SUCCESS → Logcat `VOICE`:
   `TTS-тест: движок недоступен`, выход;
2. файл `File(context.cacheDir, "tts_test.wav")` —
   `/data/user/0/org.opencode.mobile.debug/cache/tts_test.wav`;
3. `setLanguage(Locale("ru"))` — **язык захардкожен**, не берётся из настроек
   (`0x026a7a`);
4. `synthesizeToFile(text, null, file, utteranceId)` (`0x026ad2`) +
   `setOnUtteranceProgressListener` (`0x026ab2`);
5. в `onDone` файл читается `readWavPcm16` и скармливается тому же
   `WhisperTranscribeService.Companion.transcribe(...)`, лог
   `TTS-тест: N сэмплов → whisper (<model>)` (`0x0209ac`).

**Важно: `MediaPlayer` и `AudioTrack` в classes5.dex отсутствуют полностью
(0 вхождений).** То есть приложение **никогда не проигрывает** озвучку — WAV
существует только как тестовый сигнал для STT. Слово «TTS» здесь означает
генератор тестового аудио, а не озвучку ответов.

Отсюда три следствия:
- «озвучка ответов» как фича сейчас не реализована вообще;
- стриминга нет by construction: сначала весь файл, потом чтение;
- если задача — «озвучивать ответы», это новая фича, а не ускорение старой.

## 11.3 Главное: проверить можно без пересборки APK

Приложение дёргает `android.speech.tts.TextToSpeech`, а значит подойдёт **любой
движок, зарегистрированный как системный TTS-движок** (`TextToSpeechService`).
В 2026 году такие есть и ставятся обычным APK:

- HayaiTTS — sherpa-onnx, 600+ голосов, 7 семейств;
- VoxSherpa — Kokoro + Piper/VITS;
- TensorSpeak — Inflect Micro/Nano;
- kittentts-android — KittenTTS.

Схема проверки: поставить APK → Настройки → Свойства → Синтез речи → выбрать
движок → в приложении нажать существующий TTS-тест. Код opencode-mobile при этом
не меняется. Для замеров это самый дешёвый путь, и он ничего не говорит о том,
что будет, если встроить движок внутрь APK — но отвечает на вопрос «какой голос
вообще лучше».

> **Правка от 03.10.2026: этот путь для нашей задачи бесполезен.** Ни в одном из
> перечисленных приложений русского **нет** — они основаны на Kokoro/KittenTTS/
> Inflect, а это en/zh и en. Ставить и слушать нечего. Путь рабочий, но не для
> нас: озвучка на русском идёт только через встраивание SupertonicTTS 3
> (`--lang=ru`), которого в готовых системных движках нет.

## 11.4 Единственный аргумент за встраивание внутрь APK

Если движком станет sherpa-onnx, он же используется на ASR (часть 19). Тогда
в APK можно убрать `libncnnwhisper.so` (49 МБ) и ggml-стек, оставив один
рантайм. Сейчас в APK три потенциальных рантайма: NCNN, ggml/Vulkan и, если
добавим ONNX Runtime, третий. **Считать это надо до решения о пересборке**,
это единственная причина, оправдывающая новый `.so`.

Побочный эффект: встраивание даёт воспроизводимость (модель в APK или в
`files/models/`, один результат на всех устройствах) и независимость от того,
что у пользователя стоит за системный движок. Но это уже плата APK.

## 11.5 Чего не делать

- **Облако** (Yandex SpeechKit, Edge-TTS, Polly): Yandex ещё и наш OAuth уже
  прокинут — технически легко, но это отправка текста наружу плюс сетевая
  задержка. Как и с распознаванием, по умолчанию это не делаем.
- **Тяжёлые модели** (XTTS-v2, GPT-SoVITS, MeloTTS через torch): не влезают в
  мобильный APK в приемлемом виде, требуют Python. Мимо.
- **Копировать код** из GPL-3.0 обёрток (HayaiTTS, VoxSherpa, TensorSpeak) в
  проект: проект открытый. Только запуск как отдельного приложения. Веса
  ZipVoice/Pocket — Apache-2.0, с ними лицензионных вопросов меньше.
- **Не выдавать `MediaPlayer` за существующую фичу**: озвучки ответов нет,
  есть генератор тестового WAV. Если задача звучит как «ускорить озвучку»,
  сначала уточнить, что именно нужно.

## 11.6 Протокол замеров TTS (тот же стенд, что в §6)

Измерять два разных числа, они отвечают на разные вопросы:

1. **Время до первого звука (TTFA)** — то, что чувствует человек: от старта
   генерации ответа до первого `write()` в `AudioTrack`.
2. **RTF (real-time factor)** — синтез/длительность. Покажет, успевает ли
   синтез за реальным временем.
3. **Пик RSS** — расход памяти на длинном ответе.

> Ссылка на «RTF on Raspberry Pi» из документации Sherpa из старой редакции
> этого протокола **снята**: это ориентир с чужой платформы, а не измерение, и
> подставить его вместо замера нельзя.

Методика:
- один и тот же текст (20–30 слов, и отдельно 200–300 слов),
- 3 прогона, `median`,
- **SupertonicTTS 3 int8 `--lang=ru`** — основной стенд; `vits-piper ru_RU` —
  для сравнения,
- русский голос обязателен, иначе замер бессмыслен,
- прослушивать результат — забрать `cache/tts_test.wav` на ПК, в приложении
  звук не проигрывается (`AudioTrack` в коде 0 вхождений),
- WER по TTS не считать (класс `Wer` — про распознавание). Метрик качества
  TTS в приложении нет; их надо определить отдельно, а не выдумывать молча.

## 11.7 Порядок работ по TTS

> **Правка от 03.10.2026: п.1 больше не работает.** Сторонние системные движки
> без русского (см. 11.3), слушать нечего. Актуальный порядок:

1. Замерить `SupertonicTTS 3 int8 --lang=ru` на SM8850: RTF, TTFA по
   предложению, пик RSS (§11.6).
2. Положить голос юзеру на прослушивание — выбрать `--sid`. Голос на русском
   есть, но какой из спикеров звучит прилично, без человека у телефона не
   определить.
3. Параллельно решить, встраиваем ли: плюс консолидация рантайма (11.4),
   минус — новый `.so` в APK.
4. Стыковка с приложением: `AudioTrack` + очередь по предложениям (§12.5).

| Vulkan | `libvulkan.so` + `libGLESv2_adreno.so` в `/system/lib64` | `ls` |
| Android | **16**, SDK 36 | `getprop ro.build.version.release` |
| ABI | `arm64-v8a` **только** | `getprop ro.product.cpu.abilist` |

Чего **нет** (проверено, а не предположено):
- `/vendor/lib64` читается (1282 файла), но там **нет** `libvulkan`/ICD и **нет**
  NNAPI-драйверов. Драйвер Adreno живёт в `/system/lib64`.
- **Нет QNN** вообще: ни `libQnn*.so`, ни `/vendor/lib64/qnn/`.
- **Нет `vulkan` ICD** в `/vendor/etc/vulkan`.

Следствие для sherpa-onnx: провайдер только **CPU**. NNAPI даст ~+9% и требует
фиксированных шейпов (динамика мешает), QNN требует статической компиляции —
**оба недоступны**. Значит GPU-оптимизация TTS тут невозможна, и это нормально:
на 8 ядрах Oryon int8-VITS должен укладываться в real-time с запасом. Это
проверяется замером, не верой.

## 12.3 Как это ложится в приложение

Новая фича, минимальный набор изменений:
1. **Настройки:** `tts_engine` (`off` / `system` / `sherpa`), `tts_voice`
   (каталог модели), опционально скорость/высота тона. Рядом с существующими
   `stt_engine` / `stt_model`.
2. **Воспроизведение:** синтез **по одному предложению целиком** (offline API
   sherpa-onnx, не колбэк — стриминга в движках нет) → PCM-чанк в `AudioTrack`
   → следующее предложение. В коде сейчас **ноль** вызовов
   `AudioTrack`/`MediaPlayer`, то есть писать с нуля. Первый звук появляется
   раньше конца генерации ответа — это и есть TTFA, ради чего всё затевается.
3. **Поток:** один worker, как сейчас устроен STT (`Sequential` + один
   dispatcher). Иначе два быстрых ответа наложатся и зазвучат одновременно.
   **Отмена:** сброс очереди несинтезированных кусков + fade-out уже играющего,
   иначе озвучка продолжится сама после нажатия «стоп».
4. **Модель:** `files/models/tts/<voice>/`, скачивание тем же `ModelDownloader`.
   Ставить в APK нельзя — APK уже ~301 МБ, и §11.4 про размер.
5. Язык: `Locale("ru")` сейчас захардкожен (`0x026a7a`) — сделать настройкой.
6. Стриминг по предложениям — отдельное требование, см. §12.5. Решение юзера от
   02.10.2026: **озвучивать по мере генерации ответа**, а не ждать конца.

## 12.4 Побочная выгода, о которой стоит сказать юзеру

Нынешний `runTtsTest` уже умеет скармливать синтезированную речь в STT. С
появлением нормального русского голоса это превращается в **автоматический
регресс-тест распознавания на синтетической русской речи**: гоняешь фиксированный
набор фраз через TTS → STT → `Wer`, без записи голоса и без микрофона. Хороший
способ ловить регрессии Whisper/Moonshine без живого человека у телефона.

## 12.5 Стриминг по предложениям — требование (решение юзера, 02.10.2026)

Озвучка идёт **по мере генерации ответа**, а не после конца. Как работает
нормальная озвучка ассистентов.

### Механика
1. Токены от LLM приходят чанками → копится текстовый буфер.
2. Буфер режется по границе **предложения** (`.` `!` `?` и перенос строки;
   можно разделить по `;`/двоеточию, если предложение не получается слишком
   длинным).
3. Накопившееся предложение уходит в синтез **целиком, offline-вызовом**;
   результат пишется в `AudioTrack`, следующее предложение ставится в очередь.
4. Разрыв на стыке слышен только если синтез предложения медленнее, чем LLM
   дописывает следующее. Проверяется замером паузы (§12.5, таблица ниже), а не
   предполагается.

Ожидаемый ориентир: **первый звук в пределах ~1 с после старта генерации**
вместо ожидания конца всего ответа. Ориентир, а не обещание — замера ещё нет.
Это и есть TTFA из §11.6.

### Требования, которые нельзя нарушать

- **Последовательная очередь синтеза.** Один worker, тот же паттерн, что у STT
  (`Sequential` + один dispatcher). Иначе два быстрых ответа зазвучат одновременно.
- **Очистка очереди по отмене.** Если юзер нажал стоп посередине, уже
  поставленные в очередь куски **нельзя доигрывать**. Нужно два действия:
  1. сброс очереди **несинтезированных** кусков;
  2. **fade-out** того, что уже играет — иначе резкая остановка на середине слова.
- **Не ждать конца потока для первого предложения.** Первый звук — сразу, пока
  генерация не завершилась.

### Компромисс по памяти

> **Правка от 03.10.2026.** Прежний текст здесь был основан на **неверном
> выводе**. Одно предложение якобы требовало `O(состояния)` памяти, и из этого
> следовал совет «синтезировать по 2–3 предложения». Первоисточник этого не
> подтверждает: README §3.3 у ZipVoice говорит обратное — текст режется на чанки
> **по пунктуации** и батчится, расход памяти **«almost constant»**, регулируется
> `--max-duration`. Рекомендация «2–3 предложения» снята как необоснованная.
> Проверять реальное потребление памяти надо замером на SupertonicTTS 3, а не
> ссылкой на чужое README.

Что остаётся верным: расход памяти должен быть **посчитан на своём железе** на
длинном ответе, и порог ограничивать явно (`--max-duration` или аналог), а не
молча копить состояние на неограниченном буфере.

Ориентиров по скорости **нет**: ни одной подтверждённой цифры. Замеров не было.

### Что замеряем

| Метрика | Как | Зачем |
|---|---|---|
| TTFA | от старта генерации до первого `write()` в `AudioTrack` | то, что чувствует юзер |
| Пауза на стыке | замер между концом одного предложения и стартом следующего | слышно ли шов |
| Пик RSS | при ответе 300–500 слов | проверка компромисса §12.5 |
| Поведение при отмене | стоп на середине | не должно продолжать звучать |

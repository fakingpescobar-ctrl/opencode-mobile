# mobile-bridge

Мост к мобильной модели opencode. Позволяет opencode-агенту на ПК (или человеку)
напрямую общаться с моделью **big-pickle**, которая крутится на телефоне
(serve на `127.0.0.1:4096` внутри приложения opencode mobile).

Транспорт: `adb forward tcp:4098 (ПК) → tcp:4096 (телефон)`. USB-кабель обязателен
(пока; потом легко переключить на туннель — в `ocmobile/tools` уже есть tunnel-скрипты).

## Требования

- Node.js ≥ 22 (fetch глобально)
- adb: `%LOCALAPPDATA%\Android\Sdk\platform-tools\adb.exe` (или env `ADB_PATH`)
- Телефон подключён по USB, на нём запущено приложение opencode mobile (serve на 4096)

## Команды

```
node bridge.mjs ping                      # связь + версия serve + активная сессия
node bridge.mjs sessions [--limit N]      # список сессий (json)
node bridge.mjs open [--title T] [--dir D] # создать сессию (и сделать активной)
node bridge.mjs ask <text> [...]          # отправить и ДОЖДАТЬСЯ ответа → stdout: JSON
node bridge.mjs chat <text> [...]         # отправить и дождаться → stdout: чистый текст
node bridge.mjs say <text> [...]          # ОГНЁМ И ЗАБЫЛ: гарантированно записать, вернуться сразу
node bridge.mjs history [--limit N]       # история активной сессии
node bridge.mjs active [--set ID]         # показать/задать активную сессию
node bridge.mjs clean                     # удалить активную сессию
node bridge.mjs abort [--session ID]      # ПРЕРВАТЬ текущую генерацию (Stop)
node bridge.mjs watch [--log FILE] [--jsonl FILE] [--session ID] [--guard]  # СТРИМ всех диалогов
node bridge.mjs relay [--session ID] [--report FILE] [--interval S] [--max-replies N] [--guard]  # АВТОПИЛОТ
node bridge.mjs recent [--limit N] [--hours H]     # последние сообщения недавних сессий
```

## watch — бродкаст диалогов в реальном времени

`watch` подписывается на глобальный SSE-стрим serve (`GET /event`) и печатает
**все** события всех сессий — в том числе диалоги, которые ведутся прямо в
приложении opencode на телефоне:

```
[00:55:10] [session] title="bridge chat" sessionID=ses_...
[00:55:10] [user] тест два
[00:55:13] [tool] ── assistant → bash: node --version
[00:55:13] [tool] ── output: v22.0.0
[00:55:14] [assistant] Test two received. How can I help you?
[00:55:14] [assistant] ✦ finish=stop tokens=10918 cost=0
```

- `--log FILE` — дублировать человекочитаемый вывод в файл (UTF-8)
- `--jsonl FILE` — писать ВСЕ сырые события в JSONL (по одной строке на событие):
  агент на ПК может читать хвост файла и догонять diff (что делал мобильный
  агент с момента последней проверки)
- стриминг идёт двумя событиями: `message.part.updated` (полные части) и
  `message.part.delta` (кусочки по полю text/reasoning) — оба обрабатываются,
  текст виден по мере генерации
- tool-calls видны сразу: имя + краткое действие + первая строка output
- `--session ID` — фильтр по одной сессии
- `--guard` — предупреждение `⚠ GUARD` при опасных tool-командах мобильного
  агента (`rm -rf`, `git push --force`, `DROP TABLE`, `del /s` и т.п.)
- авто-reconnect (до 3 попыток с паузой 2с)
- текст стримится диффами по мере генерации, финиш сообщения помечается `✦`
- tool-calls видны сразу: имя инструмента + краткое действие (command/query/путь),
  затем первая строка output

## say — вмешаться без ожидания

`ask` ждёт завершения генерации (до 120с) и при таймауте клиента serve может
вообще НЕ записать сообщение. Для вмешательства в уже работающего мобильного
агента — `say`: дочерний процесс держит POST до конца (не рвёт соединение,
запись гарантирована), CLI возвращается сразу:

```
node bridge.mjs say --session ses_... "не туда пошёл, переделай так..."
```

Ответ агента после вмешательства смотрится через `watch` / `recent`.

## abort — прервать мобильного агента

Если бродкаст показал, что мобильный агент поехал не туда (крутит долгий
tool-call, делает опасное действие, отвечает невпопад) — можно остановить
текущую генерацию:

```
node bridge.mjs abort                      # активная сессия
node bridge.mjs abort --session ses_...    # конкретная сессия
```

`abort` отправляет `POST /session/{id}/abort` (тот же эндпоинт, что кнопка
Stop в приложении). Безопасно в любой момент: если модель не думает — abort
просто ничего не делает. После abort можно отправить корректировку через
`ask --session ID "не туда пошёл, делаем так..."` — и мобильный агент
продолжит с учётом поправки.

## relay — автопилот-наблюдатель (проактивное вмешательство)

`watch` пассивен: он пишет, но сам не реагирует. `relay` — фоновый демон,
который опрашивает сессию каждые `--interval` секунд и сам шлёт мобильному
агенту реакции по правилам (для «бродкаста», когда ПК-агент не может крутить
цикл руками):

```
node bridge.mjs relay --session ses_... --report relay.jsonl --interval 20 --max-replies 5 --guard
```

Идея: реагировать ТОЛЬКО когда есть реальный повод и мобильный агент ждёт/
застрял/совершает опасное. Автопилот смотрит на то, что агент ответил
(текст, tool-calls), и не дублирует сообщения.

Правила срабатывания (только на НОВЫЕ сообщения; первый тик — «холодный
старт», просто запоминает состояние, чтобы не комментировать прошлое):
1. **Ошибки в выводах** (error / failed / timed out / unable to connect / ...)
   — вопрос «что пошло не так»; один раз на конкретную ошибку (по сниппету).
2. **Зацикливание** — один и тот же tool + одинаковый вход вызван 2+ раза →
   короткая подсказка «смени подход или объясни, что мешает».
3. **Опасные команды** с `--guard` — пишет `guard`-строки в report (паттерны
   те же, что у watch: `rm -rf`, `git push --force`, `DROP TABLE` и т.п.).

Autopilot НЕ комментирует завершение хода (finish), не дублирует свои
сообщения и не спамит: каждая реакция — один раз (дедуп по тексту), пауза
между реакциями ≥ 3 минут, лимит `--max-replies` на сессию. Сообщения шлются
только когда есть реальный повод (ошибка/зацикливание/опасность/триггер), а
не «для галочки» — агент сам скажет «проверь с ПК», когда ему нужна проверка.

## Триггер-договор с мобильным агентом (pc-inbox.jsonl)

Мобильный агент НЕ зовёт ПК на каждую мелочь — только по явным триггерам,
которые ставит в конце своего сообщения:

| Триггер | Когда агент его шлёт | Что делает ПК |
|---|---|---|
| `проверь с ПК` | закончил фикс/изменение файла | авто-проверка MCP с ПК (`GET /mcp`) + ответ фактами; ПК-модель смотрит глубже |
| `шаг застрял` | непонятное поведение (висящий SDK и т.п.) | ПК-модель ищет исходники/доки, подсказывает |
| `проверь исходники` | анализирует код (APK, SDK, конфиги) | ПК-модель скачивает свежие исходники с GitHub, сверяет |
| `большая задача` | начало/конец многошаговой работы | ПК-модель сверяет план и итог |

Механика: relay распознаёт триггер в НОВОМ сообщении ассистента и пишет запрос
в `pc-inbox.jsonl` (рядом со скриптом) — «ящик входящих» для ПК-модели:
`{"ts":..., "trigger":"verify_pc|stuck|check_src|big_task", "label":..., "mid":..., "text":...}`.
Для `проверь с ПК` relay дополнительно сам делает `GET /mcp` через forward и
сразу отвечает агенту краткой сводкой статусов (одна реакция, дедуп по mid).

ПК-модель при чтении inbox отвечает агенту через `say` — коротко и по делу.

Флаги:
- `--session ID` — какая сессия (по умолчанию активная)
- `--report FILE` — JSONL-лог всех реакций (для чтения ПК-агентом)
- `--interval S` — период опроса (по умолчанию 25)
- `--max-replies N` — максимум авто-сообщений агенту (по умолчанию 3, защита
  от спама — после исчерпания пишет `reply_skipped` в report)
- `--guard` — предупреждать при опасных tool-командах

Реакции шлются тем же механизмом, что `say` (fire-and-forget, запись
гарантирована, генерацию мобильного агента не блокирует).

## Бродкаст-схема (агент ПК ↔ агент на телефоне)

```
ПК (build-агент)  ◄─── watch (SSE /event) ────  телефон (мобильный агент)
      │                                              ▲
      └──────────── ask / abort (HTTP POST) ──────────┘
```

- Слежение: фоновый `node bridge.mjs watch --log watch.log --jsonl watch.jsonl --guard`
  пишет всё, что делает мобильный агент: текст, tool-calls, финиши.
- Вмешательство: `ask --session ID "поправка/подсказка"` — пишет в его сессию
  напрямую; `abort` — стоп-кран.
- Совместная работа: ПК-агент видит шаги мобильного, может сам провести ту же
  диагностику на ПК (`curl http://127.0.0.1:4098/...` через forward) и вернуть
  готовый ответ/инструкцию мобильному агенту.

`recent` — быстрый снимок (без фонового процесса): последние N сообщений из
сессий, обновлённых за H часов. Для агента отдаёт JSON в stdout.

Флаги `ask/chat`:
- `--new` — новая сессия (становится активной)
- `--session ID` — конкретная существующая сессия
- `--` — терминатор: всё после него — текст сообщения (можно слать слова типа `--new`)

## Использование из opencode-агента

`ask` пишет в stdout один JSON с полем `answer` (чистый текст ответа модели)
плюс метаданные: `sessionID`, `model`, `provider`, `tokens`, `cost`, `finish`.

Ошибки — в stderr как `{"error": "..."}`, exit code 1. `usage` — exit 2.

Пример для агента (PowerShell):
```powershell
$r = node C:\Projects\ocmobile\tools\mobile-bridge\bridge.mjs ask "как дела?" --new | ConvertFrom-Json
$r.answer
```

Контекст диалога сохраняется: активная сессия пишется в `state.json` рядом со
скриптом; следующий `ask` без флагов продолжит её.

## Файлы

- `bridge.mjs` — вся программа (self-contained, без зависимостей)
- `state.json` — активная сессия (создаётся автоматически)

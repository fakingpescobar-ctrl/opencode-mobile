## 21.11 — Quality-gate: LLM не выбирает чанки (ЗАВЕРШЕНО)

**Что сделано:** после фиксации модели по latency поставил quality-gate на 20
gold-вопросах. Ядро отдаёт 6 кандидатов, модель выбирает до 3. Обёртка v5
получила `lb_gen` (генерация текста) и `lb_gen_g` (GBNF); CI run
`44635871475`, коммит `59bf6c221ef9…`, `.so` sha `de220aed7626…`.

**Ход отладки (важно):** с примером в системном промпте модели дословно
копировали `"why":"кратко почему"` — цифры были фиктивными. Без примера Qwen
выдал голый массив, gemma — `id` вместо `ids`, SmolLM2 повторил промпт.
Попытка GBNF-ограничить формат уронила Bun segfault внутри FFI-моста —
отдельный долг, не вина моделей. Итоговый gate разбирает ответы гибко.

**Результат:** `КАЧЕСТВО_ЛЛМ.md`, `quality-gate.json`. Разбираемый ответ
60/10/25%, recall 24/0/6% у Qwen3-0.6B / gemma-3-270m / SmolLM2 против **65%**
у простого детерминированного топа ядра. Все модели проиграли ядру.

**Вывод:** архитектура усилена — «код не только решает, но и выбирает». LLM
остаётся опциональным сопроцессором для объяснений/переформулировки, выбор
чанков и поле `why` остаются детерминированными. gemma быстрым режимом не
фиксируется. Запись в `ВЫБОР_МОДЕЛИ_LLM.md` §4 обновлена.

**Осталось:** интеграция ядра в `memory.js` + APK; загрузчик GGUF в диагностике;
расследование segfault в GBNF-мосте; замер RSS. Живой код не тронут, APK `apk-40`.

## 21.11 — Реальный LLM-бенч и фиксация модели (ЗАВЕРШЕНО)

**Что сделано:** по слову Макса сначала замерили latency на нашем железе,
и только потом зафиксировали модель. 7 GGUF (`models.json`) скачаны со сверкой
sha256 и размера. Первый прогон выявил три искажения: в документе указан старый
`b10000` (хотя уже собраны на `b12554`), LFM2.5 выдал EOS на 13-м токене и его
«640 мс» были несравнимы, всем моделям скормлен ChatML. Переписал обёртку
(версия `llama-bench-musl-3`): нейтральный промпт, ровно 24 токена, позиция EOG
в отчёте, число токенов промпта. CI run `44628399625` зелёный, коммит
`026bb4b325e2…`, `.so` sha `286562156fbb…`. Перегнал 7 моделей × (1 прогрев +
3 повтора).

**Результат:** `БЕНЧМАРК_ЛЛМ.md` + `bench-results.json`. TTFT/decode/24 токена:
gemma-3-270m 169/37.0/795, lfm2.5-350m 257/37.2/875, smollm2-135m 270/37.2/889,
qwen3-0.6b Q4_K_M 433/27.0/1286, qwen3 Q2_K 591/21.5/1665, lfm2.5-1.2b 749/21.9/1798,
lfm3-1.7b 1080/17.4/2408. **Выбор — Qwen3-0.6B Q4_K_M**: apache-2.0, 397 МБ,
sha `ac2d9771…`, минимальный размер с рабочим structured JSON, лучшая
стабильность (разброс 84 мс). Полный разбор — `ВЫБОР_МОДЕЛИ_LLM.md`.

**Осталось:** quality-gate на structured JSON/rerank (latency меряли, качество
нет); замер RSS; сравнение с KleidiAI-сборкой; загрузчик модели в вкладке
диагностики; интеграция ядра в живой `memory.js` и APK. Живой код не трогался,
APK остаётся `apk-40`.

## 20.11 — адаптивная семантика и бенчмарки ядра памяти
**Что сделано:** встроен `russian-stemmer.js` (Snowball, MPL 2.0, 15 КБ, без
зависимостей) + идея fuzzysearch; добавлены якоря и query-aware authority;
создан `memory-adaptive.js` (confidence по `peak`, бюджеты, concept-нить,
самообучение `memory_feedback`); `memoryPack()` переведён на паковку по score;
`runBench()` получил gate регресса ≤2 п.п.; добавлен `runAdaptiveBench()`.
**Результат:** recall@5 0.60 → **0.95**, MRR 0.29 → **0.60**, nDCG 0.36 →
**0.687**; адаптив 19/20 попаданий при −17.4% токенов, 3.1 мс/запрос.
Тесты: раннер `opencode/run-core-tests.sh` → `memory-core.test.mjs`, **109/109**,
0 падений, идемпотентно. Найдены и исправлены 2 бага: отсутствовала таблица
`graph` в `CORE_SCHEMA`, `as_of:0` игнорировался из-за falsy-проверки.
Архитектура и замеры — `АРХИТЕКТУРА_ПАМЯТИ.md` §6.2–6.3.
**Осталось:** интеграция в живой `memory.js` + Kotlin-копирование спутников,

## 21.11 — Бенч-рантайм llama.cpp на железе: .so грузится

**Что сделано:** CI-сборка `libllama-bench.so` под musl aarch64 доведена до зелёной
(`run 44625208753`, коммит `1fe11def6…`). За это время исправлены: недоступный
`musl.cc` (тулчейн Zig через apt/ziglang.org), исчезнувший тег `b4680` → `b10000`,
API llama.cpp (нет `llama_batch_add`, `struct`-теги, `llama_model_load_from_file`),
статическая линковка (`BUILD_SHARED_LIBS=OFF` + `GGML_STATIC=ON`, `--whole-archive`),
линковка через `zig c++` + `-static-libstdc++`. Найдены и зафиксированы альтернативные
ядра/форки — `MOBILE_AGENT/ИССЛЕДОВАНИЕ_ЯДЕР_LLAMA.md`: KleidiAI даёт +59% decode
на 8 Gen 1; `GGML_CPU_ALL_VARIANTS` требует `GGML_BACKEND_DL`, поэтому в нашей
статической сборке он не используется; там же LFM3-1.7B (404 582 ↓, Q4_K_M 1100 МБ).
Скачивание артефакта переписано через central directory ZIP (у GitHub data descriptor).

**Результат:** артефакт `llama-bench-musl-arm64`, `.so` 52 312 976 б, sha
`2a38bfc4e11bc95a41ba4475e64e306dd6bd75a7ddf3485b60cd7788b627f1fd`; символы
`lb_bench`/`lb_version` внутри, внешних `llama_*` нет. Загрузка через
`libldmusl.so` + `bun:ffi` из `/data/user/0/org.opencode.mobile.debug/files/musl/`
прошла: `lb_version = llama-bench-musl-2`. Инструменты:
`MOBILE_AGENT/tools/llama-bench/{build-llama-musl.yml,llama-bench-wrapper.c,download-so.mjs,ffi-smoke.mjs}`.

**Осталось:** скачать GGUF-кандидатов со сверкой sha256, прогнать замер latency
(prefill, первый токен, decode tok/s, всего, токены) на 8 ядрах, записать таблицу
в `MOBILE_AGENT/`, и только после этого фиксировать выбор модели. Живой `memory.js`
и APK не трогались, остаётся `apk-40`.

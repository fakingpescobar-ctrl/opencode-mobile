## 3. Инцидент с индексом и его закрытие

Сразу после установки живой `memory_bench(core)` показал 0.950, gate `FAIL`,
а `diag-live-recall.mjs` нашёл единственный промах g11
(«версия sdk android 17 device CPH2747», ожидали `АРХИТЕКТУРА_ПАМЯТИ.md`).
Офлайн-индекс из тех же документов и того же кода давал 1.000.

Причина найдена по FTS: у якоря `apk` bm25 почти нулевой во всех 529 чанках,
поэтому порядок в `anchor_fts` определяется rowid вставки. Инкрементальные
переиндексации за историю сборок перемешали rowid; нужный чанк оказался за
пределами якорного пула (18) и получил `anchorScore=0`. Проверены и отвергнуты:
увеличение пула 18 → 24/32/40/60 (g11 поднимается только до 8-го места и
завышает другие источники), добавление редкого якоря `deviceprofile` (живой core остаётся 0.950,
офлайн падает до 0.950).

Проверенное решение — одноразовая полная пересборка производного индекса живой
БД без изменения кода:

1. Бэкап: `архивы/BD-backup-before-rebuild-20261120.sqlite`.
2. Очищены только `doc_fts`, `anchor_fts`, `doc_chunks`, `doc_sources`.
3. `indexDocs(ROOT, {refresh:true})` — 20 файлов, 529 чанков.
4. Возвращено исходное `created` всем 529 чанкам (возраст не сброшен).
5. Таблицы `memory_fact`, `memory_staged`, `memory_audit`, `graph`, `bench_result` не тронуты.

После этого живой core 1.000 / gate pass, hard 1.000, `index_sha`
`749ebf7e3aad59f1` без изменений. После записи коротких указателей в
`СОСТОЯНИЕ.md` и `ЖУРНАЛ.md` индекс обновился до `7bd244e759a5d566`,
core остался 1.000 / gate pass, hard — 1.000 по всем метрикам.
Скрипт обслуживания и отчёт —
`opencode/opencode-cache/rebuild-live-index.mjs` и `rebuild-live-index.json`.

**Известное ограничение:** при будущих инкрементальных правках документов
порядок `anchor_fts` снова может сместиться. Полное лечение — детерминированный
ранжировщик якорного пула вместо bm25 по общему якорю; отдельная задача, в
apk-53 не входила. Диагностические скрипты лежат в `opencode/opencode-cache/`
и в индекс не попадают.

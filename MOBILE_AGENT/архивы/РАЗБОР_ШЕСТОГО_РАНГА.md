# Разбор «шестого ранга» (20.11)

По просьбе Макса дожимали h07 и p06, которые в живом замере не попадали в топ-5.

## Что на самом деле произошло

**h07** («инструмент полного снимка графа») закрылся сам после обновления
документов: в живом индексе ожидаемый `СОСТОЯНИЕ.md` стоит на 4-м ранге
(`expect_any` включает его), правки ранжирования не потребовалось.

**p06** («какие порты слушает сервер памяти») ждал не тот эталон. В старой
таблице парафраз значился `АРХИТЕКТУРА_ПАМЯТИ.md`, но порты 4199/4200/4201
описаны только в `ХАРНЕС.md` — проверено поиском по файлам. В живом индексе
`ХАРНЕС.md` стоит на 5-м ранге, то есть запрос уже закрыт. Исправлен эталон
парафразы в `tools/llama-bench/llm-coprocessor-bench.mjs`: теперь p06 ждёт
`ХАРНЕС.md`. Это гигиена эталона, не подгонка под результат.

## Настоящий дефект, найденный по пути

После дедупликации одинакового текста `sourceRank()` заменяет stale-копию
корневым эталоном, но **не пересортировывает** массив. У эталона score ниже,
поэтому топ-N перестаёт быть отсортированным по убыванию. Живой пример p06:

```
1. 0.4396 ПРАВИЛА.md      <-- замена на эталон, старая позиция
2. 0.6940 АРХИВ_СОСТОЯНИЯ.md
...
6. 0.4341 АРХИТЕКТУРА_ПАМЯТИ.md
```

Исправление в `recallDocs()`: после дедупа `dedup.sort((x, y) => y.score - x.score)`.
Добавлен регресс-тест 4f с синтетической БД: stale-копия с высоким score,
эталон с низким, третий чанк посередине. Без сортировки порядок ломается,
с сортировкой — убывает.

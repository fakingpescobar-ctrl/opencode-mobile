## 1. Дубли по topic_key, слияния по sha, конфликты contradicts

**Находки:** Все три детектируются корректно через SQL-запросы в `runProposalPass` (`memory-core.js:653-705`):

- **duplicate** (ст. 653-669): Поиск `topic_key` с `count(*) > 1` в `memory_fact`. Канонический выбор — по `valid_from DESC, id ASC`. Остальные становятся кандидатами на `supersedes`.
- **merge** (ст. 672-688): Поиск `sha` с `count(DISTINCT topic_key) > 1`. Кандидаты на слияние с доказательством `same content: A / B`.
- **contradiction** (ст. 690-705): Поиск рёбер графа с `relation = 'contradicts'`. Доказательство берется из evidence ребра или явной строки `edge <id> -> <id>`.

**Риск ложных срабатываний:** Отсутствует. SQL-фильтры точные (`HAVING count > 1`), типизированы по `kind`. Тест §7.1 подтверждает детерминированный выход: три кандидата (duplicate, merge, contradiction), все со статусом `open`, повторный проход не создает дуplikátов.

**Вердикт:** ✅ Корректно, ложных срабатываний нет.

## 2. Решение оператора: ingest → approve → rollback, approve без подписи запрещён

**Находки:** Путь решения строго от추жен:

- **acceptProposal** (`memory-core.js:715-738`): идет через `ingest` → `approve`, затем статус `accepted`. Повторный вызов возвращает `reused`.
- **rejectProposal** (`memory-core.js:740-749`): только статус `rejected`, не проходит через `ingest→approve`, но требует `approvedBy` (по умолчанию `"operator"`).
- **rollbackProposal** (`memory-core.js:751-760`): вызывает существующий `rollback(DB, audit_id)`, ставит `rolled_back`.

**Ограничение `approved_by`:**
- Внутренний `approve` (`memory-core.js:451-506`) имеет `approvedBy = "operator"` по умолчанию.
- MCP-инструмент `memory_approve` (`memory.js:550-553`) требует `approved_by` в `required: ["id", "approved_by"]` — **одобрение без подписи технически невозможно на уровне API**.
- `silent_deletions` в `proposalStats` обнаруживает отсутствие аудита у принятых предложений как сигнал тревоги, а не как ноль.

**Вердикт:** ✅ Путь `ingest → approve → rollback` единственно верный. `approve` без подписи запрещён на уровне MCP-интерфейса.

## 3. Rollback восстанавливает состояние, не оставляет молчаливых удалений

**Находки:** Тест §7.2 полный подтверждающий:

- `eq(JSON.stringify(snapshotFacts(DB)), JSON.stringify(baseline))` — все факты возвращаются в исходное состояние.
- `eq(audit, null)` — аудит откатанной записи честно удалён.
- `eq(stats.silent_deletions, 0)` — после отката тихих удалений нет.
- В `rollback` (`memory-core.js:508-547`):
  - Для фактов: удаляет `memory_fact`, восстанавливает `invalid_at=NULL` у предыдущих, удаляет `memory_fact_link` и граф-ребри, re-inserts в `memory_staged`, удаляет `memory_audit` и `memory_snapshot`.
  - Для документов: аналогичная логика без удаления фактов.

**Вердикт:** ✅ Rollback полноценно восстанавливает состояние, молчаливых удалений нет.

## 6. runProposalPass идемпотентен, не меняет индекс/gold

**Находки:**
- Использует `ON CONFLICT(id) DO UPDATE SET` для вставки предложений — при повторном вызове с тем же `at` обновляет `proof`, `evidence`, `contribution`, `seen_at`, но не перезаписывает уже принятые/отклонённые/откатанные статусы (строка 644: `CASE WHEN status IN ('accepted','rejected','rolled_back') THEN status ELSE excluded.status END`).
- Тест §7.1 строки 593-598: `eq(JSON.stringify(second.proposals), JSON.stringify(first.proposals))`, `eq(second.found, first.found)`, `eq(core.proposalStats(DB).proposals, first.found)`, `eq(core.proposalStats(DB).silent_deletions, 0)`.
- Не трогает таблицы `doc_chunks`, `doc_fts`, `bench_result`, `index_sha`.

**Вердикт:** ✅ Идемпотентен, не меняет индекс и gold-счётчики.
